|-------|-------|-------|

## Status Badge Contract

This phase centers on status badges in the list page. The badge contract is locked from the existing implementation:

| Status | Color | Label | Glyph |
|--------|-------|-------|-------|
| pending | `#94a3b8` | Pending | – |
| running | `#93c5fd` | Running | ◌ (spinning) |
| completed | `#4ade80` | Completed | ✓ |
| paused | `#fbbf24` | Needs review | ⏸ |
| failed | `#ef4444` | Failed | ✗ |

Badge style: `border: 1px solid {color}; border-radius: 4px; padding: 2px 8px; font-size: 14px; font-weight: 400; background-color: #1e293b; color: {color}; display: inline-block;`

The "running" badge on the list page does NOT need the CSS `spin` animation. The spin animation is only on the detail page step cards. The list page uses a simple text badge (no glyph animation needed — job-level status, not step-level). This is a deliberate simplification: the list page badge confirms "the job is running" without implying step-level activity.

Source: `badgeStyle()` and `badgeLabel()` functions in `+page.svelte` (verified)

## Interaction Contract

### Polling Behavior (PIPE-23)

This phase adds no new visible UI components. The interaction contract is:

| Trigger | Behavior |
|---------|----------|
| Page load with ≥1 job having `status === 'running'` | 1s polling starts automatically — no user action |
| Poll tick | Status badges in the Recent Runs table refresh reactively |
| All jobs leave `running` state | Polling stops automatically — no user action |
| New job starts (operator submits New Run form) | `$effect` re-evaluates; polling resumes if new job is `running` |
| Operator navigates to detail page | Component unmounts; polling cleans up via `$effect` cleanup fn |

**No new UI controls are added.** The `aria-live="polite"` wrapper already on the jobs table (`<div aria-live="polite">`) ensures screen readers announce badge changes during polling. No additional ARIA work needed.
