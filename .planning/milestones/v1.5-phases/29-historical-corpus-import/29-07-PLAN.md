<objective>
Close the single BLOCKER gap recorded in 29-VERIFICATION.md (gap #13 / 29-REVIEW.md CR-01): `ArgumentMetadataResponse.argued_date` in `api/schemas/utterance.py` is typed as non-optional `datetime.date`, but `pipeline/commands/import_convokit.py`'s `_parse_argued_date` legitimately returns `None` for real historical `cases.jsonl` rows lacking a parseable transcript date. `Argument.argued_date` is nullable at the DB/model layer (`api/models/models.py:175`, unchanged by this plan — no migration needed). Because FastAPI/Pydantic v2 validates outgoing responses, any historical argument landing with a null `argued_date` currently raises `ResponseValidationError` -> HTTP 500 on `GET /arguments/{argument_id}/utterances`, taking down the argument detail page, its CORPUS-10 attribution note, and the D-06/D-12 draft-review safety net.

While auditing for duplicates of this exact pattern (per this gap's own investigation mandate — grep `argued_date` across `api/`), this plan also found and fixes `CaseItem.argued_date` in `api/schemas/cases.py`, which has the identical non-optional-over-nullable-column defect. It is not reachable today because `api/services/cases.py`'s `get_cases()` filters `WHERE Argument.published_at.isnot(None)` (drafts never appear on the public `/cases` list), but it will 500 the entire public case list the moment any corpus-imported draft with a null `argued_date` is ever published — fixing it now avoids a second, near-identical gap-closure round later. This plan also found that one of the three frontend pages consuming `argued_date` (`app/src/routes/cases/[slug]/+page.svelte`, the multi-argument case picker) has no null-guard in its `formatDate()`, unlike its two siblings — this plan brings it to parity so the value this fix makes reachable for the first time actually renders correctly rather than crashing client-side.

Purpose: An operator must be able to review any corpus-imported draft argument (including the ~unknown-but-nonzero subset with unparseable/missing `cases.jsonl` transcript dates) before publishing it, and the public site must never 500 once such an argument is published.
Output: Two schema type-widenings (no migration, no service-layer change), one frontend parity fix, and regression tests proving the previously-reported failure mode cannot recur undetected.

**Explicitly out of scope for this plan** (do not touch): the 4 WARNING-level robustness gaps 29-REVIEW.md/29-VERIFICATION.md already logged as non-blocking backlog items (no unique constraint on `oyez_*` columns; `pipeline/corpus/loader.py`'s missing per-line JSON error handling; the silent `SideEnum.UNKNOWN` counter gap in `import_convokit.py`; `import_justices_csv.py`'s date-parser exception handling). Also out of scope, and NOT to be fixed here even though it was noticed while reading `pipeline/commands/import_convokit.py` during this plan's own read_first: `_import_conversation` creates its `PipelineRun` with `step="ingest"` (line 335), while `api/services/arguments.py`'s `get_argument_with_utterances()` filters for `PipelineRun.step == "parse"` (line 87) when deciding which run's utterances to show — meaning a corpus-imported argument's `GET /arguments/{id}/utterances` response will return `utterances: []` regardless of this plan's fix. This is a separate, previously-undiscovered defect from a different root cause than the argued_date nullability gap this plan closes; it does not block this plan's specific truth (200 status + `argued_date: null`, not 500) since an empty utterances list is a valid 200 response. Flag for a follow-up gap/backlog item — do not fix here.
</objective>
