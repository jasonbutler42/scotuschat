## Summary

This is a pure wiring/integration phase — no new libraries, no new architecture, no schema/migration work. Both requirements have almost all of their supporting backend infrastructure already built by earlier phases; the gap is narrowly in how the two `/admin/arguments/*` frontend routes consume that infrastructure.

**AEDIT-04's biggest research finding:** the "two save-target options" open question flagged in CONTEXT.md is **already resolved by existing code** — `PATCH /api/admin/arguments/{argument_id}/metadata` (`update_argument_metadata()` in `api/services/admin_arguments.py`, lines 786-870) already exists, already accepts `source_dockets: list[str]`, `question_number: str` (free text, parsed server-side), `argued_date`, and `case_name` (all `Optional`, only-write-if-provided semantics). This endpoint was built in Phase 19/23 specifically to back the pipeline job detail page's `ArgumentDetailsCard` consumer — it needs **zero backend changes** to also back the arguments/[id] page's new card. No schema extension, no new endpoint, no service changes. The planner should choose Option 2 (parallel save action) exactly as it already exists on the pipeline page: a new named SvelteKit form action (`saveArgumentDetails`) that PATCHes this same existing endpoint, mirroring `saveJobMetadata` almost line-for-line but simpler (no job-fetch-to-derive-argument_id step needed, since `params.id` on this route *is* the argument_id directly — no indirection through a job row).

**DASH-02's finding:** the dashboard side (CTA hrefs) is already fully built and correct — confirmed the three CTAs in `app/src/routes/admin/+page.svelte` already link to `?status=draft`, `?status=published`, `?status=unpublished`. The gap is entirely in `/admin/arguments`'s own `load()` + backend not reading that param. `api/services/admin_people.py::list_people(db, is_justice, missing, tenure_gaps)` is a directly analogous, recently-built (Phase 27) precedent for adding an optional filter parameter to a list service function and its route — the plan should mirror that shape precisely for `list_arguments(db, status=None)`.

**Primary recommendation:** Treat this phase as two small, mostly-independent, low-risk changes to `/admin/arguments/[id]` (page restructure + new form action, zero backend changes) and `/admin/arguments` + its 3 backend layers (add one optional `status` filter, following the `list_people` precedent exactly). ### Pattern 1: New form action mirrors `saveJobMetadata` but is simpler (no job indirection)

**What:** `saveJobMetadata` (pipeline page) has to fetch the job first to derive `argument_id` server-side, because the route param there is `job_id`, not `argument_id`. On `/admin/arguments/[id]`, `params.id` **is already** the argument_id — no extra fetch needed.

**When to use:** The new `saveArgumentDetails` action on `app/src/routes/admin/arguments/[id]/+page.server.ts`.

**Example (adapted from the verified pipeline pattern, `app/src/routes/admin/pipeline/[job_id]/+page.server.ts` lines 504-584):**
```typescript
// Source: pattern adapted from saveJobMetadata (pipeline/[job_id]/+page.server.ts:520-584)
saveArgumentDetails: async ({ request, params, fetch }) => {
	const data = await request.formData();
	const dockets = (data.getAll('docket[]') as string[])
		.map((v) => v.trim())
		.filter(Boolean);
	const question_number = ((data.get('question_number') as string) ?? '').trim();
	const argued_date = ((data.get('argued_date') as string) ?? '').trim() || null;

	// No job-fetch needed here — params.id on THIS route is already the argument_id
	// (unlike saveJobMetadata, which must derive it from the job row first).
	let res: Response;
	try {
		res = await fetch(
			`${FASTAPI_BASE_URL}/api/admin/arguments/${params.id}/metadata`,
			{
				method: 'PATCH',
				headers: {
					'X-Admin-Token': ADMIN_TOKEN,
					'Content-Type': 'application/json',
				},
				// case_name intentionally omitted — this page's Case card owns case_name
				// via the unchanged ?/save action (D-03 — do not double-write case_name).
				body: JSON.stringify({
					source_dockets: dockets,
					argued_date,
					question_number: question_number || null,
				}),
			},
		);
	} catch {
		return fail(502, { saveError: 'Could not save. Try again.', dockets });
	}

	if (!res.ok) {
		return fail(422, { saveError: 'Could not save. Try again.', dockets });
	}

	throw redirect(303, '/admin/arguments/' + params.id);
},
```

**Note on redirect vs. `update()` pattern:** the pipeline page's `saveJobMetadata` returns `{ saved: true, refreshResolveRows: true }` rather than redirecting, because `ArgumentDetailsCard`'s own `use:enhance` handler calls `update({ reset: false })` on success (see the component's `use:enhance` block, lines 66-78) — it does NOT expect a redirect. **The existing `/admin/arguments/[id]/+page.svelte`'s other actions (`save`, `publish`, `unpublish`) DO redirect(303)** on success. The planner must decide consistently: since `ArgumentDetailsCard.svelte` is unmodified (D-03 explicitly reuses it byte-for-byte) and its own `use:enhance` already handles the non-redirect case correctly (calling `update({reset:false})`), **the new `saveArgumentDetails` action should NOT redirect** — match the pipeline page's `saveJobMetadata` return-value convention (`return { saved: true }`, no redirect) so the component's built-in success/error message rendering (`form?.saved` / `form?.saveError`, lines 212-234 of the component) actually fires. A `redirect(303,...)` would bypass the component's own success-message UI entirely and is inconsistent with how the component was designed to be used.

### Pattern 2: `load()` builds `savedValues`/`hints` exactly like the pipeline page

**What:** `ArgumentDetailsCard` expects `savedValues: {dockets, question_number, argued_date}` and `hints: {dockets, question_number, argued_date, case_name}`. The pipeline page's `load()` already builds these from an `ArgumentPreview`-shaped object (lines 220-243 of `pipeline/[job_id]/+page.server.ts`). The arguments/[id] page's `load()` already fetches the full `ArgumentDetail` (which is a superset of what pipeline's `ArgumentPreview` needs — it already has `source_dockets`, `question_number`, `cover_metadata`, `argued_date`), so this is a direct copy-adapt, not new logic.

**Example:**

### Anti-Patterns to Avoid

- **Client-side array filtering of `data.arguments`:** Would work visually but doesn't match `list_people`'s established server-side-filter pattern and doesn't satisfy DASH-02's actual gap (D-06 explicitly requires threading `status` through all 3 layers: `+page.server.ts` → router → service).
- **Adding `dockets`/`question_number` fields to `ArgumentUpdate` (the `?/save` PATCH body):** Unnecessary — `MetadataUpdate` + its existing `/metadata` endpoint already covers this. Extending `ArgumentUpdate` instead would create two competing PATCH paths writing overlapping Argument columns and re-introduce exactly the confusion CONTEXT.md's D-01/D-02 already resolved.
- **Merging `case_name` into `ArgumentDetailsCard`:** Explicitly forbidden by D-03 — the component was never designed to hold it (`hints.case_name` prop exists but is dead/unrendered, confirmed by reading the component template — no `{hints.case_name}` reference anywhere in `ArgumentDetailsCard.svelte`).
- **Redirecting after `saveArgumentDetails` success:** Would bypass `ArgumentDetailsCard`'s own built-in success-message rendering — see Pattern 1 note above.
- **Re-deriving `argument_id` via a job fetch inside the new action:** Unlike `saveJobMetadata`, this route's `params.id` already IS the argument_id — no indirection needed.

## Common Pitfalls

### Pitfall 1: Double-writing `case_name` from two actions on the same page
**What goes wrong:** If the new `saveArgumentDetails` action's PATCH body ever includes `case_name`, and the operator has unsaved edits in the Case card's `case_name` field, whichever form is submitted last silently overwrites the other's in-flight edit (no conflict warning).
**Why it happens:** `MetadataUpdate` accepts an optional `case_name` field (built for `saveJobMetadata`'s use case, which the pipeline page's code comments explicitly guard against sending — see `WR-02` comment in `saveJobMetadata`, "case_name is intentionally omitted here").
**How to avoid:** Follow the exact same `WR-02` guard on the new action — never include `case_name` in the `saveArgumentDetails` PATCH body. Case card's `?/save` action remains the sole owner of `case_name` writes.
**Warning signs:** If the plan's new action's `JSON.stringify(...)` body includes `case_name`, flag it — it duplicates a write path that already exists via `?/save`.

### Pitfall 2: Forgetting `argued_date` must be removed from the Case card's `?/save` payload
**What goes wrong:** D-03 moves `argued_date` into `ArgumentDetailsCard`. If the Case card's existing `?/save` action still sends `argued_date` in its form body (it currently reads a hidden/visible `argued_date` input — see current `+page.svelte` lines 192-215), two different actions on the same page write the same column, and the Case card's now-removed `argued_date` input would submit `''` (empty string), which the backend's `update_argument()` treats as "provided" — `datetime.date.fromisoformat('')` raises → 422 on every Case-card save.
**Why it happens:** The `argued_date` `<input type="date">` is currently inside Card 1's single `<form>`; splitting Card 1 requires physically removing that input from the Case card's form, not just relocating it visually.
**How to avoid:** When restructuring `+page.svelte`, delete the `argued_date` input entirely from the Case card's form (do not just leave it hidden) and delete the corresponding `formData.get('argued_date')` line from the `save` action in `+page.server.ts` (or leave it but only forward it if non-empty — safer to delete outright per D-03's "old form is reduced" framing).
**Warning signs:** A 422 on saving the Case card that mentions `invalid_date_format` after this phase ships.

### Pitfall 3: `source_dockets` empty-array vs. `null` semantics on first save
**What goes wrong:** `update_argument_metadata()`'s normalization (lines 822-834) treats an empty `source_dockets` array as "clear the field" (`None`), same as the pipeline page's established `D-06` pill-restore contract. If the arguments/[id] page's `load()` fails to seed `savedValues.dockets` correctly from `argument.source_dockets` (or falls back incorrectly when it's `[]` but `source_docket` is set), an operator could accidentally submit an empty pill list and silently null out an existing docket.
**Why it happens:** `argument.source_dockets` defaults to `[]` (not `null`) per `ArgumentDetail` schema (`source_dockets: list[str] = []`) — a `[]` from the API does not necessarily mean "no docket," it could also mean "only `source_docket` is populated" (older data, pre-Phase-23-multi-docket).
**How to avoid:** Use the exact same fallback the pipeline page's `load()` already uses (Pattern 2 above): `argument.source_dockets?.length ? argument.source_dockets : (argument.source_docket ? [argument.source_docket] : [])`.
**Warning signs:** An argument that has a `source_docket` value but empty `source_dockets` array shows an empty pill list on this page after the phase ships (visible immediately in manual verification).

### Pitfall 4: Route-ordering hazard if a new literal route is added under `/arguments`
**What goes wrong:** `api/routers/admin.py` has explicit comments (T-19-03-05 pattern) that literal-segment routes (`check-duplicate`, `stats`, `recent-drafts`, `metadata`) MUST be registered before the parameterized `GET /arguments/{argument_id}` route, or FastAPI will try to parse the literal segment as an `int` path param and 422.
**Why it happens:** This phase does NOT add any new literal route (the `status` filter is a query param on the existing `GET /arguments` list route, and `saveArgumentDetails` reuses the existing `/metadata` route) — but if a planner mistakenly proposes a new endpoint instead of reusing `/metadata`, this ordering hazard applies.
**How to avoid:** Confirm the plan reuses `PATCH /arguments/{argument_id}/metadata` (already correctly positioned in the file, after `/publish` and `/unpublish`, before the parameterized `DELETE`) rather than adding a new route.
**Warning signs:** Any plan task titled "add new endpoint for ArgumentDetailsCard save" should be treated as a red flag — the endpoint already exists.

### Pitfall 5: `status` query param collision with `ArgumentListItem`'s existing `status` field name
**What goes wrong:** None expected — `status` as a query param name doesn't collide with anything server-side (FastAPI query params and response model fields are independent namespaces), but worth flagging since `ArgumentListItem.status` is also a field name in the same response. No actual pitfall here, just a naming-clarity note for the planner: the query param `status` (string, `'draft'|'published'|'unpublished'`) is unrelated to fetching `Argument.status` — no code conflict, just don't let it cause hesitation.
**How to avoid:** N/A — confirmed safe by inspection of the FastAPI route signature pattern used by `is_justice`/`missing`/`tenure_gaps` on the People route, which has an analogous field-name/param-name overlap concern (`is_justice` param vs. implicit Person.is_justice column) and works fine today.
