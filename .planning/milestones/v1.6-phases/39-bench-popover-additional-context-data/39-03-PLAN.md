<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Operator browser → SvelteKit `save` action | Untrusted form input (including a hand-crafted `tenures` JSON payload) crosses into a server action. |
| SvelteKit action → FastAPI admin PATCH | Server-to-server call authenticated by the `X-Admin-Token` header; the Pydantic schema is the mass-assignment boundary. |
| FastAPI → PostgreSQL | `_replace_tenures` writes operator-supplied values into the constrained column. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-39-09 | Tampering | `PersonUpdate` / `TenureWrite` mass assignment | medium | mitigate | `PersonUpdate` already declares `extra="forbid"`; the two new fields are added to the explicit allow-list only. `TenureWrite.reason_left` is a strict `Literal` over exactly the three canonical values, so a hand-crafted `tenures` JSON carrying an arbitrary reason is a 422 before the service runs — the `<select>` escape-hatch option is a display affordance, never a write allowance. |
| T-39-10 | Tampering | `update_person()` `death_date` write | medium | mitigate | Guarded by `"death_date" in fields_set`, not a null check. Without this, the photo/bio form's PATCH (a different action carrying a different field subset) would clear a stored death date on every save — a silent operator-data-destruction path. Pinned by a named `model_fields_set` regression test in Task 1. |
| T-39-11 | Elevation of Privilege | newly-activated editor controls | low | accept | No new route, action, or auth boundary is introduced. Both fields ride the existing `X-Admin-Token`-protected PATCH and the existing HMAC-session-gated admin area; the authorisation posture is unchanged. |
| T-39-12 | Repudiation | operator edits to the two new fields | low | accept | Consistent with every other field on this editor, these writes are not individually audit-logged. Introducing per-field audit logging is a project-wide concern, not a Phase 39 scope item. Accepted with the existing posture. |
| T-39-SC | Tampering | npm/pip/cargo installs | n/a | accept | No package installs in this plan. `39-RESEARCH.md` §"Package Legitimacy Audit" records zero new packages. |

No `high`-severity threat is present in this plan. Stored-XSS on the escape-hatch option's

covered by `/gsd-secure-phase` and code review, not minted as a phase-specific control.
