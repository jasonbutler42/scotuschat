<objective>
Close 39-UAT.md gap 1: the operator added a bio to a Justice through the admin editor, the
textarea kept showing the typed text, and nothing was saved.

The cause is a submit-path ownership problem, not an API problem. `bio_text` is submitted only
by the Bio & Photo form, whose only submit button is **Upload photo** inside the Photo card.
The page's primary affordance — the **Save Person** button at the bottom — posts the `save`
action, which deliberately omits `bio_text` from its PATCH body. An operator who types a bio and
presses Save Person therefore submits everything except the bio. Two further defects turn that
into a *silent* loss rather than a visible one: the `photo` action's person PATCH never checks
its response and discards any error, and the textarea carries its stored value as child text
content, so the browser's dirty-value flag keeps the typed string on screen after the reload —
exactly what the operator described.

This plan moves ownership of `bio_text` to the save form (where the operator already expects it),
removes the swallow-the-error path, and makes the textarea display persisted state.

The API layer is already correct and is not touched: `PersonUpdate.bio_text` exists,
`update_person` writes it under a `model_fields_set` guard, and
`api/tests/test_admin_people.py::test_update_person_partial_patch_does_not_wipe_other_fields`
already proves a bio-only PATCH persists. Plan 39-03 is also not the cause — it added
`death_date`/`reason_left` to the same two files and never touched the bio path; the defect
predates Phase 39 and surfaced now because D-14 made the bio publicly visible for the first time.

Purpose: an operator can save a bio and believe what the screen tells them.
Output: one save button that saves the whole person, and a regression test that keeps it that way.
</objective>
