**Areas discussed:** Validation strategy, Enforcement layers

---

## Validation strategy

| Option | Description | Selected |
|--------|-------------|----------|
| Strict allow-list | Reject anything that isn't digits-dash-digits (optionally a short suffix). Matches existing DOCKET_RE precedent. | |
| Permissive sanitize | Strip/reject only filesystem-dangerous characters (path separators, `..`, quotes, control chars) but otherwise allow free text. | ✓ |

**User's choice:** Permissive sanitize.
**Notes:** Chosen over strict docket-shape enforcement to avoid rejecting legitimate-but-non-standard docket-like values; strict format enforcement noted as a deferred idea for a future phase if wanted.

---

## Enforcement layers

| Option | Description | Selected |
|--------|-------------|----------|
| Defense-in-depth | FastAPI Pydantic Field pattern (create_job route) AND a hard sanitizer immediately before the filesystem write in ingest.py, optionally mirrored in the frontend. | ✓ |
| Single hard boundary only | Validation at just the FastAPI Pydantic layer (create_job route). | |

**User's choice:** Defense-in-depth.
**Notes:** ingest.py is also invoked as a standalone offline CLI script per this project's architecture (CLAUDE.md), which bypasses the FastAPI layer entirely — the second boundary is required, not optional, for that reason.

## Deferred Ideas

- Strict real-SCOTUS-docket-format enforcement (`"22-915"` shape) at the operator-input layer — deferred in favor of permissive sanitization for this fix.
- Frontend (`DocketPillInput.svelte`) inline validation feedback — optional, not required for the security fix itself.
