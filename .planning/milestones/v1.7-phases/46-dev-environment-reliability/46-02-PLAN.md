  </action>

  <instructions>
    Open PowerShell **as Administrator** on the Windows host and run these in order. `<CIDR>` is the WSL subnet Claude just printed (e.g. `172.26.32.0/20`); `<GATEWAY>` is the gateway IP (e.g. `172.26.32.1`).

    1. Discover the service and its real data directory — do not assume the generic install path:
       - `Get-Service -Name 'postgresql-x64-18' | Format-Table Name, Status, StartType`
       - `(Get-CimInstance Win32_Service -Filter "Name='postgresql-x64-18'").PathName`
         The `-D "<path>"` argument in that output is the authoritative data directory holding `postgresql.conf` and `pg_hba.conf`. Record it.
    2. Set the service to start automatically and start it: `Set-Service -Name 'postgresql-x64-18' -StartupType Automatic; Start-Service -Name 'postgresql-x64-18'`
    3. Edit `<datadir>\postgresql.conf`: set `listen_addresses = '*'` (uncommented). Rationale to record: `listen_addresses` only controls which interfaces the server binds; pinning it to `<GATEWAY>` would break service startup after any reboot that shifts the NAT subnet. Access control is enforced by the next two steps, which ARE narrowly scoped.
    4. Edit `<datadir>\pg_hba.conf`: add exactly one host line, `host    all    all    <CIDR>    scram-sha-256`. Do **not** use `0.0.0.0/0`, `::/0`, `172.0.0.0/8`, or `trust`. Leave the existing `127.0.0.1/32` and `::1/128` lines untouched.
    5. Add a scoped inbound firewall rule:
       `New-NetFirewallRule -DisplayName 'PostgreSQL 5432 from WSL' -Direction Inbound -Protocol TCP -LocalPort 5432 -RemoteAddress <CIDR> -Action Allow -Profile Any`
       If a rule for 5432 already exists from a prior setup attempt, inspect it first with `Get-NetFirewallRule -DisplayName '*5432*' | Get-NetFirewallAddressFilter` and narrow or remove any rule whose `RemoteAddress` is `Any`.
    6. Apply the config changes: `Restart-Service -Name 'postgresql-x64-18'`
    7. Create the application role and both databases, matching the naming already documented in `README.md`. Use the same URL-safe password you will put in `.env` (plan 46-03 writes it):
       - `createuser -h localhost -p 5432 -U postgres -W -P scotus`
       - `createdb   -h localhost -p 5432 -U postgres -W -O scotus scotus`
       - `createdb   -h localhost -p 5432 -U postgres -W -O scotus scotus_test`
       If `createuser`/`createdb` are not on `PATH`, they are in the service's `bin` directory alongside the data directory found in step 1.
    8. Confirm from the Windows side: `Test-NetConnection -ComputerName <GATEWAY> -Port 5432` reports `TcpTestSucceeded : True`.

    Then, back in WSL, Claude verifies the WSL-side half and writes the evidence file:
    - `timeout 5 bash -c 'cat < /dev/null > /dev/tcp/<GATEWAY>/5432' && echo REACHABLE`
    - Create `.planning/phases/46-dev-environment-reliability/46-WINDOWS-POSTGRES-SETUP.md` recording, with the date: the discovered data directory path, the exact `listen_addresses` value set, the exact `pg_hba.conf` line added, the exact `New-NetFirewallRule` command run (no passwords), the `Get-Service` status output, the role/database names created, and the WSL-side reachability probe result. Record any place the real Windows install differed from 46-RESEARCH.md's generic guidance (that is Assumption A1 being closed out).
  </instructions>
