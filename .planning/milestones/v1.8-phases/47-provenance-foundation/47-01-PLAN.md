<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Decide the closed-vocabulary representation for source and method</name>
  <decision>Represent `import_run.source` and `import_run.method` as native PostgreSQL enum types (`import_source`, `import_method`) or as `varchar` + `CHECK` constraints?</decision>
  <context>
CONTEXT.md files this under "Claude's Discretion" and names the trade-off explicitly, so it is
NOT a decision the operator has already made — which is why it earns a gate here while D-01
(drop `pipeline_runs`) and D-05 (drop `utterance.strategy`) do not.

This is a one-way door. PostgreSQL cannot drop a value from an enum type. Once
`import_source` ships with `operator/corpus/pdf_pipeline/seed` and `import_method` ships with
`manual/direct/normalized/rule_based/llm_corrective`, retiring a value later means "add the
new one and stop using the old one" — the exact situation STATE.md already records as a
carried blocker for `argument_status` (`pipeline` cannot be dropped; Phase 48 must add
`candidate` alongside it). Undoing the choice entirely requires a new Alembic migration that
converts the columns to varchar and drops both types.

RESEARCH.md recommends native PG enum on evidence from this codebase: 5 of 7 existing
enum-shaped columns use `SAEnum(..., values_callable=...)` (`SideEnum`, `PipelineRunStatus`,
`AdminJobStatus`, `AdminJobStep`, `ArgumentStatusEnum`); only `CourtTenure.office` and
`CourtTenure.reason_left` use varchar+CHECK, and the model's own comments frame those as late,
narrow two/three-value additions rather than a table's primary discriminator. `source` and
`method` ARE the primary discriminator of `import_run`.
  </context>
  <options>
    <option id="native-pg-enum">
      <name>Native PG enum types `import_source` / `import_method` (RESEARCH.md recommendation)</name>
      <pros>Database-level exhaustiveness — an out-of-vocabulary write is rejected at the storage boundary (ASVS V5, threat T-47-06). Matches the dominant in-repo idiom, so `models.py` stays internally consistent. The DO-block-guarded `CREATE TYPE` idiom from migration 0003 applies verbatim.</pros>
      <cons>A value can never be dropped. Adding a value later needs `ALTER TYPE ... ADD VALUE` outside a transaction (the migration-0008 dance). Milestone v1.8 phases 48–50 add vocabulary to *other* enums, so this pattern's cost is already familiar and already accepted project-wide.</cons>
    </option>
    <option id="varchar-check">
      <name>`varchar(50)` + `CHECK` constraint (the CONTEXT.md alternative)</name>
      <pros>Vocabulary evolves with an ordinary `ALTER TABLE ... DROP CONSTRAINT` / `ADD CONSTRAINT` — values can be removed as well as added. Matches `CourtTenure.office` / `reason_left`.</pros>
      <cons>Breaks consistency with the five enum columns already in `models.py`, including `import_run.status` itself (which stays a native enum either way, since `pipeline_run_status` is only being renamed). Loses the SQLAlchemy `SAEnum` typing that the ORM layer and every downstream phase's comparison sites would otherwise get for free.</cons>
    </option>
  </options>
  <resume-signal>Select: native-pg-enum, varchar-check, or describe an alternative. Task 2 assumes native-pg-enum unless told otherwise; if varchar-check is selected, swap the two `CREATE TYPE` statements for `sa.String(50)` columns plus named CHECK constraints and use plain string columns in the ORM, leaving every other instruction in Task 2 unchanged.</resume-signal>
</task>
