<objective>
Close three defects and one approved enhancement found live during the 48-08 operator
checkpoint, all on the `/admin/arguments` list page plus one backend correctness fix.

1. **Defect 1 (regression Phase 48 introduced):** the list page's `publish` action
   discards every non-ok response and always redirects — a below-threshold Publish click
   looks like nothing happened. Fix it the same way plan 48-08 already fixed the identical
   problem on the detail page.
2. **Enhancement (approved, overlaps Defect 1):** render the block reason on the list
   page and let the operator submit an override reason directly from a row, plus a
   passive per-row trust-tier badge. Explicitly rejected alternative, not implemented:
   disabling the Publish button below threshold — the operator wants the override path
   to stay reachable from the list, not removed.
3. **Defect 2 (pre-existing invariant bug):** unpublishing does not hide an argument from
   the public site, because the public read paths gate on `published_at` (deliberately
   retained per D-02) rather than on `status`. Fix by adding a `status == PUBLISHED`
   condition to all three public read paths — `get_cases`, `get_argument_with_utterances`,
   and `get_argument_speakers` (a third site the originating todo did not name), not just
   the two functions the todo identified.

Purpose: the detail page (48-08) already gives the operator sight and override authority
over a blocked publish; the list page — the screen the operator actually works from day
to day — silently ate the exact same failure. Separately, the operator's only takedown
control (Unpublish) currently takes nothing down, which undermines TRUST-04's entire
premise that promotion is a single meaningful gate.

Output: a working list-page publish-block-and-override UI addressed per row, a passive
tier badge on every row, a corrected public-visibility filter across three service
functions with a regression test, and a static source contract locking the frontend
behavior.
</objective>
