## D-35 (locked 2026-08-24, operator, during Phase 49 gap-closure execution)

**Decision:** *"If an argument is currently published, the data for that argument is locked. If an argument is in any other state, I expect the data to be editable and have almost the exact interface."*

The operator was offered three mechanisms for G-49-3 (`deep-link`, `port-control`, `defer`) and rejected the framing itself, saying: *"I'm less concerned about the mechanisms behind the scenes and the decisions that came before that led us here but I feel like they are tripping us up."* They then selected **"Converge both surfaces."**

D-35 has two halves. This plan implements the FIRST half on the participant path. Plan 49-10 implements the second half and retires `T-15-02-BENCH` as satisfied. The decision is locked: it is not to be re-litigated, and no task in either plan may emit a checkpoint asking it again.

**Scope boundary of this plan (deliberate, recorded, not a silent reduction):** D-35 says *"the data"*, which is broader than participant sides. The full inventory of write paths and their disposition is Task 3's `deferred-items.md` entry. One genuinely NEW question falls out of it and is recorded there for the operator — it is a different question from G-49-3, not a re-ask.
</locked_decisions>

<planner_decisions>
**Why the published lock is a plan of its own rather than a task inside the convergence.**
It is a tightening on already-published data; the convergence is a loosening on unpublished data. They fail differently, they are reviewed differently, and one of them is urgent. Landing the lock first also produces the strongest single compensating control for retiring `T-15-02-BENCH` in 49-10: once the lock exists, no reclassification from this surface can ever mutate live public data. Writing the loosening first would mean shipping, however briefly, a repo where BENCH is settable on a published argument.

**Why the guard must sit BEFORE the authority gate, not beside it.**
`apply_participant_value_change` records a `value_discrepancy` as part of deciding a write (D-16). If the published check ran after it, a refused edit would still leave a discrepancy row and a `review_state` advance behind — a rejected write with side effects, which is worse than either accepting or refusing cleanly. `update_resolve_row_for_job` already orders it this way (its guard list is numbered 1-2-3 in the docstring, with the status check at 2 and the participant SELECT at 3). Copy that order; make the ordering an executable assertion, not a comment.

**Why the predicate is `== PUBLISHED` and not `!= DRAFT`.**
The folded todo `2026-08-21-widen-participant-editability-to-all-unpublished-states` exists precisely because the resolve writer's ORIGINAL guard was CANDIDATE-only and had to be widened. Writing a narrower predicate here would re-introduce the bug that todo closed, on a second path, one commit after the first was fixed. There must be a live test proving an UNPUBLISHED argument still accepts the write, or the widening is asserted only by comment.

**Two stale docstrings in the same neighbourhood are corrected here, because leaving them would actively mislead the reader of the code this plan touches.** `api/routers/admin.py`'s resolve-row endpoint still documents the pre-widening rule (*"Rejected once the linked argument has left the 'candidate' status"*) and still documents the pre-RESOLVE-13 descriptor rule (*"descriptor is forced to null server-side whenever side == BENCH"* — the service in fact leaves the column untouched, preserving the stored value). Both statements are now false. Since this plan's whole claim is *"the two participant writers read identically on the published question,"* a reader comparing them would be misinformed by exactly these two lines. Correcting them is docs-only and carries no behavioural risk.

**Why `resolve_participant_review` is NOT given a published lock, and why that is not an inconsistency.**
`api/services/admin_review.py::resolve_participant_review` writes only `review_state` — never a value column. Under D-35, review metadata is not *"the data for that argument"*: marking a published row confirmed, or re-flagging it, changes nothing a member of the public can see. Locking it would also break the review queue for exactly the rows most likely to need auditing. Recorded as an intentional non-hole so a future reader does not file it as a miss.

**WR-01's behavioural question is small enough to answer here, and it is answered: resync on OPEN, not on every prop change.** 49-REVIEW.md's own suggested fix (`:327-334`) is the same. Resetting on open cannot lose operator input, because the popover is closed and no input exists. Resetting on *every* `initialSide` change would discard a radio choice the operator deliberately made while the popover was open — a worse bug than the one being fixed. So no effect tracking the prop; one branch on the open transition.

**No tracer task.** 49-01's tracer already threaded this phase's architecture; every layer this plan touches is shipped. There is no new layer to thread.
</planner_decisions>
