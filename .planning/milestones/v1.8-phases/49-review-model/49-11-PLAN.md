If an argument is in any other state, I expect the data to be editable and have almost the exact interface."* At the end of 49-09's run the planner recorded a scope question in `deferred-items.md` rather than raising it as a checkpoint: does *"the data for that argument"* mean participant data only, or the whole argument — the Case card and the Argument Details card too? The orchestrator put it to the operator on 2026-08-24. They answered: **whole argument, lock everything.** That includes argued date, case name, docket, and question number.

**That answer is LOCKED (recorded here as D-35a). No task in this plan may emit a checkpoint asking it again.**

**Why this plan exists as its own wave.** 49-09 locked participant writes. 49-10 converged the participant interface and used 49-09's lock as its compensating control for retiring `T-15-02-BENCH`. Across those two plans the page is deliberately HALF-LOCKED: on a published argument the Speakers card is read-only and explains itself, while the Case card and the Argument Details card sit right above it, fully editable, saving straight through to `update_argument` and `update_argument_metadata`. 49-09 left that state on purpose and said so — it refused to silently reverse a recorded decision. The operator has now reversed it. **The half-locked page is explicitly NOT the operator's desired end state, and this plan closes it.**

**What is actually open, all verified in source before this plan was written:**
- `api/services/admin_arguments.py::update_argument` freezes only the SLUG on a published argument — its own docstring says *"PUBLISHED or UNPUBLISHED: slug is frozen; only `lead_case.case_name` is updated."* `argued_date`, `docket_number`, `docket_number_norm`, and `case_name` all remain writable on live public data.

<planner_decisions>
**Why four inline guards and not one extracted helper.** Six functions will carry this guard after this plan. A shared predicate helper is the obvious engineering instinct and it was rejected for two concrete reasons. First, it cannot be applied to the two pre-existing sites without editing `update_participant_side` (owned by 49-09) and `update_resolve_row_for_job` (Phase 25's, and the reference shape everything else copies) — so a helper would produce a repo where four sites call a helper and two carry inline guards, which is strictly worse than six identical inline guards. Second, the only pure-domain home for it (`api/domain/`) holds model-free modules; a helper there would have to take a status string rather than the `ArgumentStatusEnum` symbol, minting exactly the third dialect this plan was told to avoid. The drift risk a helper would remove is instead removed by an executable parity assertion across all six functions. If a seventh writer appears without the guard, that assertion fails.

**Why the shared error prose prefix is the frontend's branch key.** `update_resolve_row_for_job` minted the message shape; 49-09 copied it verbatim onto `update_participant_side`; this plan copies it onto four more. Every one of them opens with the argument id followed by the same published-status clause. The SvelteKit actions branch on that shared clause, which means one dialect across every surface and no new machine token to keep in sync. A token like the existing `slug_collision` was considered and rejected: adding one here would require adding it to 49-09's message too, and 49-09 owns that function.

**Why both guards reuse an already-loaded Argument row instead of selecting one.** This is not a performance nicety, it is a test-contract constraint discovered by reading. `api/tests/test_admin_arguments_service.py` drives `update_argument_metadata` three times with an `AsyncMock` whose `db.execute.side_effect` is a fixed ordered list, and `test_metadata_update_null_final_pair_does_not_collide` asserts `db.execute.await_count == 1`. An extra SELECT breaks all three. Both target functions already load the Argument as their first act, so the guard is a comparison, not a query. An executable assertion pins the SELECT count so a future refactor cannot quietly reintroduce one.

**The three mock-driven tests DO need one edit, and it is an addition, not a weakening.** Their `SimpleNamespace(id=7, source_docket=..., question_number=...)` stand-in has no `status` attribute at all, so the guard would raise `AttributeError` before reaching the logic under test. Each fixture gains an explicit non-published status. That is the fixture catching up to a column the function now legitimately reads — no assertion is removed, no expectation is relaxed, and the SUMMARY must say so plainly rather than reporting "3 tests updated."

**Why `resolve_job` and `create_person_for_job` are locked even though the published case is not reachable today.** I traced it: a PAUSED job is required by both; `AdminJob` rows are minted PAUSED only by the corpus importer (which skips any conversation whose argument already exists) and by the PDF ingest path (which always creates a NEW argument and rejects duplicates on the `(source_docket, question_number)` constraint); and both paths that stamp `Argument.resolved_at` — the precondition `publish_argument` requires — also drive the job to COMPLETED. So no current path produces a PAUSED job pointing at a publishable, let alone published, argument. That makes these guards defence in depth. They are still worth writing, because the control that blocks the published case today is an **indirect** one, living in a different table's lifecycle, and any future change to how jobs bind to arguments would remove it silently and without a failing test. This is the same reasoning `delete_argument`'s own docstring already applies to its client-side disable: the server-side gate is the authoritative one. Severity is recorded as medium, not high, precisely because reachability is currently blocked — the plan does not overstate its own urgency.

**Why `merge_people` and `update_person` are NOT locked, and why that is the one genuinely ambiguous call.** `merge_people` repoints `ArgumentParticipant.person_id` and `Utterance.person_id` across every argument the source person appears in, published ones included — so by a literal reading of *"lock everything,"* it writes a published argument's data. But a `Person` is shared: locking it would mean one published argument freezes that person for every other argument forever, which for a sitting Justice means permanently. That cannot be what *"lock the whole argument"* asks for, and choosing it would be a planner inventing policy. So it is left unlocked, recorded as ambiguous, and surfaced as this plan's one NEW operator question. It is a different question from the one the operator just answered: that one was about which CARDS on the argument page are locked; this one is about data that is not owned by any single argument.

**Why the page states the lock once, at page level, rather than per card.** 49-09 put an explanatory line inside the Speakers card because that card was the only locked one. Under D-35a the whole page is locked, and three separate card-level reason lines would be noise that says the same thing three times. One page-level statement covers the Case card and the Argument Details card, and 49-09's Speakers line stays untouched because its assertions pin it and because it names a control-specific remedy. This is a judgment call about copy density, made in the open; the human-check is what closes it.

**Why the `ArgumentDetailsCard` component itself is not touched.** Its existing readonly mode already does exactly what is needed — it disables the docket pill control, the question-number field, and the argued-date field, drops the "Use extracted" affordance, and stops rendering its Save button, while keeping every `CopyableExtractedValue` hint live. That mode is already exercised by the pipeline page. Passing the flag is a one-prop change at the call site; editing the shared component would put a second consumer at risk for no gain.

**No tracer task.** 49-01's tracer threaded this phase's architecture and every layer this plan touches has shipped. There is no new layer to thread.
</planner_decisions>
