<objective>
Give the operator the two argument-scoped actions the `AdminJob` removal takes away or newly enables: a real argument-scoped approve (D-14) reachable over HTTP, and delete-in-every-state-except-published (D-25) with its latent FK defect fixed (D-26). Also stamp operator provenance on the five `Argument`/`Case` compare-set columns so the ladder's `operator` rung is actually live on those two tables.

Purpose: `approve_job` is currently the only writer of `resolved_at`, and `publish_argument` refuses on `resolved_at IS NULL` as a non-overridable gate — plan 50-01 shipped the service function, this plan puts it behind an authenticated route so a corpus argument is publishable by a human, not only by `reset_to_fixture`. D-26 is a MUST-FIX found during discussion: `delete_argument`'s cascade never touches `value_discrepancy`, which carries `import_run_id` as a hard FK, so deleting an argument with any recorded discrepancy raises `ForeignKeyViolation`. It is latent today only because almost nothing creates discrepancies yet — D-01's always-reconcile makes it routine and D-25 makes the candidates newly deletable.

Output: one new authenticated route, operator provenance stamping on two service functions, an inverted delete gate, a corrected cascade, and a test that actually deletes an argument carrying discrepancies.
</objective>

<decision_record>
**PD-08 (restated — this plan implements it).** `Argument` and `Case` have no `review_state`, so operator authority on their five compare-set columns can only be read off `source == "operator"`. Phase 49's D-22 rule that an operator edit does not rewrite stored provenance is scoped to the two tables that HAVE a `review_state`; applying it to `Argument`/`Case` would leave the operator rung unreachable and let a corpus re-import clobber an operator edit, contradicting SC-3. Recorded as a deliberate, scoped deviation from D-22's letter.

**PD-10 — the approve surface is `/admin/review`, not `/admin/arguments`.** Verified at plan time: `list_arguments` filters to DRAFT/PUBLISHED/UNPUBLISHED, so a freshly-imported CANDIDATE corpus argument does not appear in `/admin/arguments` at all, while `/admin/review` includes CANDIDATE in its status filter set and is the screen Phase 49 built for exactly this sweep (D-19: no new screen). This plan ships the ROUTE; plan 50-04 puts the button on the review row.

**PD-11 — the delete gate is INVERTED, not extended.** The current gate is a single positive condition (`status != DRAFT` refuses). D-25 requires published-only refusal. Adding a second branch would leave two predicates that can drift; the condition becomes one published-only refusal and the docstring's rationale paragraph is rewritten to match, including retiring the now-false claim that CANDIDATE is blocked because an active AdminJob may still reference it (corpus arguments no longer have one, and a PDF job's `argument_id` is NULLed by cascade step 6 regardless).
</decision_record>
