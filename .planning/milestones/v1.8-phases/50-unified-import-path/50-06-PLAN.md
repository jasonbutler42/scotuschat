<decision_record>
**PD-18 — D-22's enumeration is treated as incomplete, not authoritative.** D-22 names `import_convokit`, `import_justices`, `parse.py` and `resolve.py`. Research reading the actual source found two specific ungated call sites inside two of those files that the enumeration does not describe: `resolve.py`'s Step 5 bulk `ArgumentParticipant.person_id` UPDATE, and `import_convokit`'s `_apply_extracted_name_provenance` Person name-part writes. Both are covered — the second by plan 50-05, which owns that file. The inventory in plan 50-07 records the discovery so a later phase does not re-derive it.

**PD-19 — `Utterance.person_id` stays ungated, on purpose.** `Utterance` carries no `source`, `method` or `review_state` column; Phase 47's D-05 dropped the per-row `strategy` column precisely because utterances inherit provenance from their parent `import_run`. There is no stored authority for the ladder to compare against, so a gate there would be theatre. Dispositioned `N/A — no authority column` with this reason, not silently skipped.

**PD-20 — `parse.py`'s participant seeding is a CREATE, not an overwrite.** It inserts `ArgumentParticipant` rows for labels that do not yet exist, with `person_id=None`. The gate functions operate on an existing ORM row and arbitrate between a stored value and an incoming one; a create has no stored value. Dispositioned `N/A — create, not overwrite`. It DOES need one change: it currently sets no `source`/`method` at all, which floors every seeded participant to UNCERTAIN via `derive_tier` (the exact defect Phase 49's D-18 fix chased). Stamp `source=ImportSource.PDF_PIPELINE` and the run's own method on the created row, matching what `import_convokit` already does for corpus participants.

**PD-21 — the D-24 gate is behavioral, and it must be able to fail.** A gate that passes because it asserts nothing is worse than no gate. `pipeline/tests/test_gated_column_writers.py` drives each writer against a real database with a pre-existing higher-authority stored value and asserts the value did NOT change AND a `value_discrepancy` row exists. It additionally contains one deliberately-constructed control: a direct ungated UPDATE of the same column, asserted to change the value and produce NO discrepancy row — proving the gate's assertions are content-dependent and would go red if a writer regressed to a direct UPDATE.
</decision_record>
