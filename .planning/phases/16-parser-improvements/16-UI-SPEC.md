## Affected Surfaces and States

Phase 16 pre-populates existing fields. The surfaces that display the results are already
built. This section documents the interaction states those surfaces must handle correctly
after Phase 16 writes data.

### Argument Edit Page (`/admin/arguments/[id]`)

**Case title field** — `<input type="text" name="case_name">`
- Pre-populated state: field displays extracted case name; operator can overwrite before saving
- Empty state (extraction failed): field displays blank; placeholder text is absent (native input behavior); operator types from scratch — same as pre-Phase-16 baseline

**Argued date field** — `<input type="date" name="argued_date">`
- Pre-populated state: field displays extracted date as YYYY-MM-DD (via `toDateInputValue()`)
- Empty state: field blank; operator enters date

**Docket field** — `<input type="text" name="docket_number">`
- Docket is set at ingest (not changed by Phase 16 per D-02/CONTEXT.md). No change to this field's behavior.

**No new UI changes to this page are required for Phase 16.**

### Pipeline Job Detail Page (`/admin/pipeline/[job_id]`)

**Argument metadata preview card** (above step timeline)
- Already renders `case_name`, `docket_number`, `argued_date` from the argument record
- After Phase 16, these fields will be non-empty for standard transcripts immediately after parse
- No new markup required; display is identical

**Advocate role dropdowns** (resolve step table and participant list)
- After Phase 16 (PARSE-02), `argument_participants.side` values arrive pre-set to PETITIONER / RESPONDENT / AMICUS / UNKNOWN instead of all-UNKNOWN
- Dropdown options and save mechanism are unchanged; Phase 16 only changes the initial selected value
- No new UI markup required

**No new UI changes to this page are required for Phase 16.**

## Phase-Specific Notes

### Why this phase has a minimal UI contract

Phase 16 is intentionally a pipeline/backend-only phase per 16-CONTEXT.md:

- PARSE-01 writes `argued_date` and `case_name` to the `Argument` and `Case` DB rows
- PARSE-02 writes initial `side` values to `argument_participants` rows
- Both extractions are fail-safe — parse step never fails due to extraction failure
- The operator reviews and corrects extracted values through the Phase 11 argument edit UI and the Phase 15 advocate role editor, which are already implemented
- No new admin page, modal, or indicator is added in Phase 16

### What a successful Phase 16 looks like to the operator

1. Operator uploads a PDF and runs the pipeline
2. After the parse step completes, the argument metadata preview card on the job detail page shows a pre-populated case title and argued date (instead of blank/placeholder values)
3. After the resolve step completes and the operator approves the argument, the advocate role dropdowns on the job detail page show pre-assigned sides (PETITIONER / RESPONDENT / AMICUS) for standard transcripts, requiring fewer manual corrections
4. The operator opens the argument edit page and sees case title and argued date already filled in — they review rather than type from scratch

### Dry-run behavior (no visual change)

Per 16-CONTEXT.md CR-05 pattern: metadata writes are skipped in `args.dry_run` mode.
No UI indicator is added to surface dry-run suppression — this is a CLI concern only.
