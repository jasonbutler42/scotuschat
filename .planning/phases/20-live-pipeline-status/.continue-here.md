# BLOCKING CONSTRAINTS — Read Before Anything Else

> These are not suggestions. Each constraint below was discovered through failure.
> Acknowledge each one explicitly before proceeding.

- [ ] CONSTRAINT: SvelteKit static-route fetch routing — `fetch('/admin/pipeline', { headers: { Accept: 'application/json' } })` inside a `setInterval` silently gets routed to the SvelteKit **page** handler (returns HTML 200), not `+server.ts`. `res.ok` is `true`. `res.json()` throws `SyntaxError`. The error is **swallowed** in an async `setInterval` callback — no console error, no visible failure. Always use `invalidateAll()` for polling on static routes.

**Do not proceed until all boxes are checked.**

## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| Direct fetch on static SvelteKit routes | `fetch('/admin/pipeline', Accept: application/json)` routes to page handler (HTML), not `+server.ts`. Error swallowed silently in async setInterval. | blocking | Use `invalidateAll()` for all polling — it re-runs the server load function directly, bypassing routing ambiguity. |
| Assuming `invalidateAll()` "has latency" | The CR-03 comment in `[job_id]/+page.svelte` says invalidateAll() has "known latency". This was confirmed WRONG — it propagates immediately after the server round-trip. | advisory | Trust `invalidateAll()`; the "latency" is just the network round-trip, not a framework bug. |
| Forgetting `data.*` props need invalidation on terminal | `liveJob` (polled via direct fetch in detail page) updates status, but `data.argument` and `data.participants` (from initial server load) don't update automatically. Post-completion UI sections stay hidden. | advisory | On terminal state transition, call `invalidateAll()` once — already implemented in commit `69100a7c`. |

**Severity values:** `blocking` — resuming agent must pass understanding check before proceeding. `advisory` — important context, does not gate resumption.
