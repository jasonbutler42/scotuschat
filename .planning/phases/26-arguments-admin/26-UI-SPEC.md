## Design System

| Property | Value |
|----------|-------|
| Tool | none — no `components.json`, no shadcn. Project uses hand-rolled inline dark-theme CSS (`style="..."` on each element), consistent across all admin routes (Phases 5–25). This is a SvelteKit/Svelte 5 project, not React/Next/Vite-React, so the shadcn gate does not apply; the existing pattern is the design system. |

## Spacing Scale

Declared values (must be multiples of 4) — extracted verbatim from existing admin pages (`arguments/+page.svelte`, `arguments/[id]/+page.svelte`, `ArgumentDetailsCard.svelte`, `RunStatusCard.svelte`):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Gap between hint-row pills/text; gap in inline flex rows (e.g. status badge + icon) |
| sm | 8px | Label-to-input gap; gap between inline buttons (Publish/Unpublish/Edit row); table cell horizontal padding |
| md | 16px | Field-to-field vertical margin within a card form; margin between stacked cards |
| lg | 24px | Card internal padding (`padding: 24px` on every card `<div>`); heading-to-content margin inside a card |
| xl | 32px | (not currently used in admin pages — reserved, no exception needed this phase) |
| 2xl | 48px | Page content top/bottom padding (`padding: 48px 24px` on the `<div style="max-width: ...">` content wrapper) |
| 3xl | 64px | (not currently used in admin pages — reserved) |

Exceptions:
- Touch targets: all buttons and submit inputs use `min-height: 44px` (WCAG 2.1 AA target size), except compact inline per-row Save buttons in tables (`min-height: 36px`, matching the existing Advocate Roles row pattern in `arguments/[id]/+page.svelte` line ~322) — carry this 36px exception forward for the new Speakers section's per-row Save buttons, since they sit inside a dense multi-row list rather than standing alone.
- Status log entries use tighter vertical rhythm than card padding: `padding: 8px 0` per log row (matches the existing table row density in `arguments/+page.svelte`), not the 16/24px card spacing.

## Typography

Extracted verbatim from existing admin pages — do not introduce new sizes/weights.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label / meta | 14px | 400 | 1.4 (established value for chip/label text; use 1.5 for paragraph-style meta text) |
| Heading (card `<h2>`) | 20px | 600 | 1.2 |
| Sub-heading (`<h3>`, e.g. RunStatusCard state titles) | 16px | 400 | 1.2 |

Only these 3 sizes (14/16/20) and 2 weights (400 regular, 600 semibold) appear anywhere in the existing admin UI. Use exactly these for all new elements in this phase (status card, status log, Speakers section, Archived badge). Do not add a 4th size or a 3rd weight.

## Component & Layout Contract (phase-specific, supplements template)

This section captures decisions the standard template categories don't have a slot for, needed by the planner/executor for this specific phase.

### List page (`/admin/arguments/`)

- Table columns, in order: **Status | Case Title | Docket | Argued | Created | Publish** (insert "Created" as a new column between "Argued" and the row-actions column, per ALIST-04). Use the existing `formatDate()` helper (already present in both `+page.svelte` files) for the Created column — same date format as Argued (`"Jun 15, 2026"` style, no time).
- Status filter: query must include `ArgumentStatusEnum.UNPUBLISHED` alongside `DRAFT`/`PUBLISHED` (fixes the ALIST-02 bug noted in CONTEXT.md's Integration Points). Do not add a client-side filter UI for status in this phase — REQUIREMENTS scope is "shows all three states," not "filterable by state."
- Row actions column logic (three-state, replaces current two-branch `{#if arg.resolved_at && !arg.published_at}` / `{#else if arg.published_at}`):
  - status === DRAFT → show "Publish" button (accent-bordered, same style as today)
  - status === PUBLISHED → show "Unpublish" button (muted-bordered, same style as today)
  - status === UNPUBLISHED → show "Publish" button (re-publish; same accent style as the Draft→Published case — no visual distinction between first-publish and re-publish buttons)
- Badge function (`badgeStyle`/`badgeLabel`) gets a third branch for `unpublished` → color `#fb923c`, label "Unpublished". Keep the existing badge markup/border/padding shape exactly as-is (`border: 1px solid {color}; border-radius: 4px; padding: 2px 8px; font-size: 14px; font-weight: 400; background-color: #1e293b; color: {color};`) — only the color/label mapping changes.

### Edit page (`/admin/arguments/[id]`) — card order top to bottom

1. **Argument Details** (existing card — unchanged by this phase, owned by Phase 23's shared component contract)
2. **Status** card — current badge + "Created {date}" (relabeled from "Resolved") + "Published {date}" (only when set) + slug (unchanged) + Publish/Unpublish button lives inside this card now (see below), not floating below all cards as it does today
3. **Status history** (NEW) — full log list, rendered directly below the Status card, visually as a sub-section within the same card OR its own card (planner's discretion per D-10-adjacent latitude — not locked by CONTEXT.md); if a separate card, use identical card chrome (`background-color: #1e293b; border: 1px solid #334155; border-radius: 8px; padding: 24px;`)
4. **Speakers** (NEW, replaces "Advocate Roles" card + tenure-gap-warning banners entirely — D-07)
5. **Danger Zone** (existing — last card, unchanged position; only the blocked-copy and gate logic change per D-03)

Moving Publish/Unpublish into the Status card (rather than leaving them as their own un-carded block between Advocate Roles and Danger Zone, as today) is a layout simplification consistent with Phase 25's "no floating buttons" principle applied elsewhere in v1.5 — the planner may keep them as separate un-carded full-width buttons immediately following the Status card if moving them inside the card proves awkward with the new Status History content; either placement satisfies AEDIT-01/08, but they must not float between Speakers and Danger Zone as an orphaned button block.

### Speakers section — column layout (single unified table/list, not two separate advocate/bench tables)

Per-row content, in order: **Name | Role | Title | Utterances | Action**

- **Advocate row:** Name (plain text) → Role `<select>` (PETITIONER / RESPONDENT / AMICUS — three options only; no UNKNOWN/"Counsel" option, unlike the current Advocate Roles card's four-option select, since AEDIT-06 lists exactly these three) → Title `<input type="text">` with an "Extracted: {hint}" row beneath it (same convention as `ArgumentDetailsCard`) → Utterances (plain number, read-only) → "Save" button (compact, 36px, `use:enhance`, inline — no full page reload, matches D-04)
- **Bench row:** Name (plain text) → Role (plain text, read-only: tenure-derived role name, or "Missing tenure" in `#fbbf24` + "Edit person" link) → Title column: em-dash `—` (bench has no title field) → Utterances (plain number, read-only) → Action column: em-dash `—` (no per-row action for bench rows; "Edit person" link lives inline with the "Missing tenure" text, not in the Action column)
- One `<form use:enhance>` per advocate row (identical to the existing Advocate Roles pattern — do not batch all rows into a single form), so each row saves independently without affecting others' unsaved state.
- Utterance count must be computed per-participant via `Utterance.argument_id` + `Utterance.person_id` (per CONTEXT.md's Integration Points note that the per-job aggregate query is not reusable) — this is a backend/data concern, noted here only because it determines that the Utterances column is always populated per row, never "N/A".

### Archived pipeline-run badge (folded todo, touches `RunStatusCard.svelte`)

- Add a 4th readiness-adjacent visual state distinct from the existing `jobStatus`-driven `BADGE_COLOR`/`BADGE_LABEL` maps: when `readiness.state === 'already_created'`, the badge shown in the card header must read **"Archived"** in `#cbd5e1`, replacing whatever `jobStatus`-derived badge (e.g. "Completed") would otherwise render in that state. This is a badge-selection-logic change (readiness state overrides job-status badge when already_created), not a new badge component — reuse the exact badge markup already in `RunStatusCard.svelte`.
