<objective>
Close UAT Gap 3 (major, found during Test 3): the /admin/people/new create form renders First/Middle/Last/Suffix inputs, but three layers of the create path silently drop them — the SvelteKit create action reads only full_name/is_justice, PersonCreateRequest declares only those two fields, and create_person sets only those two on the new row. Only Full Name persists; the name parts are discarded. The [id] editor's save action is the working reference (it reads and forwards all four).

Per debug diagnosis (.planning/debug/create-person-discards-name-parts.md), this is an implementation gap, not a scope decision: D-08 (27-CONTEXT.md) names only tenure/bio/photo/birthdate as deferred on create — it never mentions structured name parts. Fix aligns create with [id] behavior (the UAT reporter's expectation is parity, not further deferral). Auto-backfilling Full Name from parts is a separate future item (backlog Phase 999.15) and is NOT in scope here.

Purpose: A person created with structured name parts keeps them, eliminating a silent-data-loss defect that has no operator-facing warning.
Output: Name parts flow end-to-end on create.
</objective>
