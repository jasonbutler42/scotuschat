<objective>
Close the two BLOCKER data-loss defects (CR-01, CR-02 in 27-REVIEW.md) that caused ROADMAP Success Criterion 4 / REQUIREMENTS.md PEDIT-07 to FAIL re-verification (27-VERIFICATION.md, status gaps_found, pass 3). Both live in a single file — `app/src/routes/admin/people/[id]/+page.svelte` — and both were documented in the phase's most recent commit (the code review, f751dee0) but never fixed.

- **CR-01:** The hidden `tenures` input and the visible `birthdate` input are nested inside `{#if isJustice}`. Toggling an existing Justice to "Advocate" un-mounts them, so on Save Person the `save` action reads their absent-defaults (`'[]'` / `null`) and sends an explicit PATCH that wipes every CourtTenure row and the birthdate. Fix: make the data-carrying inputs always present (outside the conditional), so the true current state is always submitted — regardless of the toggle. This is exactly PEDIT-07's "unchecking hides fields but does not delete tenure or appointment data" clause, and it upholds the service layer's documented tenure-preservation intent (Phase 18 D-06/D-07) which is currently defeated because `body.tenures` arrives as `[]` (not `None`).
- **CR-02:** The person-id-change reset `$effect` resets `isJustice`/`birthdate`/merge state but omits `tenureRows`/`nextKey`. The `merge` action redirects to `/admin/people/{target_id}` on the same route (soft navigation reuses the component), leaving `tenureRows` holding the pre-merge source person's data. A subsequent Save overwrites the target's real tenures with stale ones. Fix: reset `tenureRows`/`nextKey` in that same effect.

Purpose: Stop a single accidental toggle + Save (or a Save right after a merge) from permanently destroying a Justice's biographical record — a "biographical records are permanent" data-integrity violation this project treats as a hard constraint.

Output: Two scoped edits to one Svelte component. No new symbols, no schema/migration, no backend changes.

**Explicitly OUT of scope (do NOT implement):**
- The WR-01..WR-04 and IN-01..IN-04 findings from 27-REVIEW.md (Warning/Info severity, not routed to gap closure).
- Any edits to 27-01 through 27-09 PLAN.md files, or to `+page.server.ts` / backend files.
- The optional Bench→Advocate confirmation dialog (27-REVIEW.md CR-01 "defense in depth" suggestion). Rationale for deferring: once CR-01 is fixed, toggling to Advocate no longer destroys data, so a confirmation prompt is no longer protecting against data loss — it would add modal/state/UX complexity for a now-benign action. The two data-preservation fixes below are the complete, non-negotiable scope.
