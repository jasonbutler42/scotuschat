<objective>
Fix a Svelte 5 `effect_update_depth_exceeded` infinite-loop regression on `/admin/people/[id]` that was introduced by the CR-02 fix in Phase 27 Plan 10 (commit `b02a2681`), diagnosed in `.planning/debug/person-detail-effect-loop.md`. This bug currently BLOCKS all 5 remaining items in Phase 27's 4th UAT retest (`27-UAT.md`) — the CR-01 data-preservation round-trip test itself failed on this exact error, and CR-02 plus 4 other carried-forward checks could not even be attempted because the page becomes unusable.

**Root cause (from the debug session, status: diagnosed):** The person-id-change reset `$effect` (currently at `app/src/routes/admin/people/[id]/+page.svelte` lines 125-150) sets the `$state` variable `nextKey = 1` and then, inside the `.map()` callback that rebuilds `tenureRows`, computes each row's `_key` via `nextKey++` — this both READS and WRITES the same `$state` variable synchronously inside the effect's own execution. Svelte 5 tracks `nextKey` as a dependency of the effect because it's read, then observes the effect's own write mutating that same dependency, so it reschedules the effect — forming an infinite rerun loop that pegs the main thread until Svelte's max-reruns guard throws. This only manifests for a person with at least one tenure row (so the `.map()` callback actually executes), which is why the codebase's automated/structural checks (27-10's grep-based `<verify>` gates) did not catch it — it required a live click-through, which is exactly what this UAT retest surfaced.

Purpose: Unblock Phase 27's 4th UAT retest by restoring a usable, non-looping person-detail page, without touching or weakening the CR-01 (always-present hidden inputs) or CR-02 (tenure/nextKey re-derivation on person-id change) data-preservation fixes 27-10 already landed.

Output: One scoped edit inside a single existing `$effect` block, in one file. No new symbols, no schema/migration/backend changes, no reversal of 27-10's CR-01/CR-02 behavior.

**Explicitly OUT of scope (do NOT implement):**
- Any change to the CR-01 fix (the always-present hidden `birthdate`/`tenures` inputs, or the visible Birth Date input losing `name`/`form`) — that code is correct and unrelated to this loop.
- Any change to the top-of-script `tenureRows`/`nextKey` initializer (lines ~54-73) or `addTenureRow`/`removeTenureRow` — both are already safe (they run outside `$effect`) and must remain byte-for-byte unchanged.
- Introducing `untrack()` or any new Svelte primitive/import not already used in this file — the established codebase convention (write-only resets, e.g. `admin/pipeline/[job_id]/+page.svelte:78`) is sufficient and is what this fix restores.
- Re-attempting the CR-01/CR-02 behavioral round-trips as automated tasks here — per the established 27-07/08/09/10 gap-closure pattern, those remain human UAT checks, now unblocked by this fix and re-tested in the next `/gsd-verify-work 27` pass.
</objective>
