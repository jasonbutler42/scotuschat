<objective>
Close a second, independent gap in Phase 29 discovered during investigation of a different reported defect (not present in 29-VERIFICATION.md's gaps list): `pipeline/commands/import_convokit.py`'s `_import_conversation` (the single PipelineRun creation site, currently at line ~333-338) creates every corpus-imported argument's `PipelineRun` with `step="ingest"`. This is the ONLY `PipelineRun` the corpus importer ever creates per argument — there is no separate "parse" or "resolve" invocation, because `import-convokit` does entity creation, speaker resolution, and utterance writing all in one command/one run (confirmed via 29-04-SUMMARY.md and 29-05-SUMMARY.md: the run is created once, before any utterance write, and every `Utterance` row created by `_import_utterances` points at that same `pipeline_run_id`).

`api/services/arguments.py`'s `get_argument_with_utterances` finds "the run whose utterances to show" by querying `select(func.max(PipelineRun.id)).where(PipelineRun.argument_id == argument_id, PipelineRun.step == "parse", PipelineRun.status == PipelineRunStatus.COMPLETED)` (line ~87). Since corpus-imported arguments never have a `step="parse"` row, this query returns `None` for every one of them, `max_run_id` stays `None`, and the function returns `{"argument": {...real metadata...}, "utterances": []}` — silently, as a 200, for every corpus-imported argument regardless of the sibling 29-07-PLAN.md's unrelated `argued_date` nullability fix. 29-07-PLAN.md's own Task 2 regression test explicitly declined to assert on `utterances` length/content for exactly this reason (it was already open when that plan was written) — this plan is what closes that gap.

**Investigation conclusions (stated here, not left open for the executor):**
1. **No admin UI displays `PipelineRun.step` directly.** Grepping `app/src/routes/admin/pipeline/` and `app/src/routes/admin/arguments/[id]/+page.svelte` confirms every step-driven badge/label in the admin UI (`RunStatusCard`, the pipeline list's compound badge, `stepStatus()` in the job-detail page) is computed from `AdminJob.current_step` — a separate enum column on the unrelated `admin_jobs` table (`AdminJobStep.INGEST/PARSE/RESOLVE`) — never from the raw `PipelineRun.step` string. Relabeling a corpus-imported run's `PipelineRun.step` has no rendering-surface impact anywhere.
2. **`api/services/admin_jobs.py`'s `get_run_id_for_step(db, job_id, step)` cannot reach a corpus-imported argument.** Every call site (`get_job`, `resolve_job`, `api/routers/admin.py`'s poll/PDF-serving endpoints) resolves `step` against a `PipelineRun` scoped by `job.argument_id`, derived from an `AdminJob` row looked up by `job_id`. `import_convokit.py` contains zero references to `AdminJob` anywhere in the file — corpus-imported arguments are never linked to an `AdminJob` row, so this generic step-keyed lookup is structurally unreachable for them. This is not a hypothetical scenario avoided by convention; it is a code path that does not exist.
3. **No backfill/data migration is needed.** `29-VERIFICATION.md`'s own Scope Note confirms `data/corpus/` contains only `.gitkeep`/`.gitignore` — no operator has run `import-convokit` against real data, and zero corpus-imported `Argument` rows exist anywhere (dev or production). This is a pure forward-looking code fix affecting only future writes.
4. **The fix does not touch the read side.** `api/services/arguments.py`'s `step == "parse"` filter is the codebase's one established, multi-consumer meaning of "the run that produced this argument's `Utterance` rows" (used identically by `admin_jobs.py`'s `get_run_id_for_step(..., "parse")` for the PDF pipeline). The corpus importer's single run IS that run (per 29-05-SUMMARY.md: every `Utterance` row it creates carries `pipeline_run_id=run.id`), so the minimal-blast-radius fix is to change what string the write side stamps, not to add a second query branch to the shared read-side contract.

The fix therefore: relabels the corpus importer's single `PipelineRun.step` from `"ingest"` to `"parse"`, adds regression assertions to the two existing pipeline tests that already query this row without checking its `step` value, and adds one new end-to-end test that runs the real `import_convokit.py` write path and the real `arguments.py` read path against the same fixture, asserting the previously-always-empty `utterances` list is now populated with the correct, correctly-ordered, correctly-attributed rows.

**Explicitly independent of 29-07-PLAN.md** (the `argued_date` nullability fix): this plan touches no file 29-07 touches, and this plan's new regression test uses a fixture case row with a parseable `transcripts` date, so it passes regardless of whether 29-07 has executed yet.

Purpose: A corpus-imported draft Argument's utterances must actually be viewable by the operator (via the argument detail page) and, once published, by the public — the entire value of CORPUS-07 (multi-sentence utterance storage) is defeated if the stored utterances are unreachable through the one read path that serves them.
Output: One corrected string literal in the pipeline write path, two updated test assertions, and one new end-to-end regression test proving utterances are retrievable, not merely that the query survives.
</objective>
