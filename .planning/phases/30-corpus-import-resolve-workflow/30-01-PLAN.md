<objective>
Fix the corpus-import write path in `pipeline/commands/import_convokit.py` so every corpus-imported argument lands in the existing AdminJob PAUSED/RESOLVE review workflow instead of being permanently stuck. This is the crux of Phase 30: two producer-side changes that make the entire (unchanged) resolve/approve/publish machinery reachable for corpus jobs.

Two research-confirmed bugs are fixed here (30-RESEARCH.md Pitfalls 1 & 2):
1. `Argument.status` is written as `ArgumentStatusEnum.DRAFT` today (line 398, Phase 29 D-06). Every read path that gates editability (`list_resolve_rows_for_job`'s `editable` flag, `update_resolve_row_for_job`'s guard, the job-detail page's `readonlyMode`) keys on `argument.status == ArgumentStatusEnum.PIPELINE`. Left as DRAFT, every corpus Resolve card is permanently read-only from creation. Change it to `PIPELINE`.
2. `AdminJob.discrepancies` is never populated for corpus jobs. ResolveCard's per-row Action column (Confirm/Change/Create person — D-05's explicit requirement) renders only when a matching `discrepancies` entry exists. Synthesize one HIT-shaped dict per resolved participant.

Scope boundary: NO "skip pause if zero flags" shortcut (D-03 overrides resolve.py's PDF-path precedent). NO bulk/batch tooling (D-04). The reused service functions (`resolve_job`, `approve_job`, `update_resolve_row_for_job`) are NOT modified — this is a producer-side fix only.

Purpose: Make the publish gate (`resolved_at IS NOT NULL`) reachable for corpus arguments for the first time, via the operator's explicit two-stage resolve→approve action.
Output: Modified `import_convokit.py` + a DB-gated test proving the new row shapes.
</objective>
