<objective>
Add a `source: Literal["pdf", "corpus"]` derived field to `AdminJobResponse`, populated at read time in both `list_jobs()` and `get_job()`, so the operator can tell a corpus-imported job apart from a PDF-ingested one. This is the backend data contract the 30-UI-SPEC.md Source tag depends on (its "Data Contract Note").

The derivation mirrors the shipped `is_archived` pattern (Phase 26, `admin_jobs.py:219-255`) but uses `exists()` instead of a raw second `outerjoin`: the `Argument → PipelineRun` relationship is 1:many (an argument accumulates multiple PipelineRun rows over reruns/step-advances), so a naive join would risk duplicate AdminJob rows in the result set. `exists()` is duplication-safe regardless (30-RESEARCH.md Code Examples).

No schema/DDL change (CLAUDE.md: Alembic is sole DDL authority) — the signal already exists in `PipelineRun.strategy == "convokit_import"` (the `PIPELINE_RUN_STRATEGY` constant Phase 29 already stamps on every corpus PipelineRun).

Scope boundary: this plan adds the field to the schema/service layer only. It does NOT add any detail-page (`/admin/pipeline/[job_id]`) UI element — 30-UI-SPEC.md's "Out of Scope Confirmation (D-05)" forecloses new detail-page UI surfaces. The list-page Source tag is 30-03's job.

Purpose: Provide a robust, non-fragile provenance signal (not "all PDF fields happen to be null") for the UI.
Output: New schema field + service derivation + a test proving corpus vs pdf classification.
</objective>
