<objective>
Resolve D-02's stored-data problem: term-1955 corpus arguments were imported by Phase 29 BEFORE this feature existed, so they sit at `status=DRAFT` with `resolved_at=NULL` and NO paired AdminJob — permanently unpublishable AND (after 30-01 ships) they would ALSO be permanently read-only in the Resolve UI if left as-is (DRAFT ≠ PIPELINE). There is no in-place fix; D-02 specifies wipe-and-rerun using the same idempotent import path, with "no separate one-off migration/backfill script needed."

This plan is therefore an OPERATOR RUNBOOK, not committed code (D-02). It must run AFTER the 30-01 write-path fix is live (that is why it is the last wave): the re-run only produces correct rows once `import_convokit.py` writes `status=PIPELINE` and inserts the paired AdminJob.

Scoping: per STATE.md and Phase 29's history, term 1955 is currently the ONLY corpus data imported, so "corpus arguments" (those whose linked argument has a `PipelineRun.strategy = 'convokit_import'`) is exactly the term-1955 batch. The wipe predicate is scoped to that set and provably never touches a PDF-ingested argument. The operator SELECTs and reviews the target argument IDs before deleting.

FK-safe delete order follows STATE.md's documented v1.4 `delete_argument` cascade, extended to delete the corpus AdminJob rows (there are none for the OLD term-1955 data, so this is defensive/idempotent for any partial re-run): AdminJob → Utterance → ArgumentParticipant → CaseArgument → PipelineRun → Argument (Cases left intact — `_get_or_create_case` is idempotent on re-run; deleting orphaned corpus Cases is optional).

People are NOT wiped: `import-justices` and `_resolve_person` are idempotent (match existing people), and the missing-name-parts data-quality gap is fixed by the operator in the Resolve/People-admin UI (the whole point of this phase), not by re-import.

Purpose: Bring the already-imported term-1955 batch into the same reviewable/publishable state as future imports.
Output: term-1955 corpus arguments re-created at status=PIPELINE with paired PAUSED/RESOLVE AdminJobs.
</objective>

    Step 1 — Identify the target corpus arguments (review this list before deleting):
    ```sql
    -- Corpus arguments = those with a convokit_import PipelineRun.
    -- Currently this equals the term-1955 batch (the only corpus data imported).
    SELECT DISTINCT a.id, a.source_docket, a.argued_date, a.status
    FROM arguments a
    JOIN pipeline_runs pr ON pr.argument_id = a.id
    WHERE pr.strategy = 'convokit_import'
    ORDER BY a.id;
    ```
    Sanity-check: every returned row should be status='draft' with the expected term-1955 argued_date range, and none should be a PDF-ingested argument.

    Step 2 — FK-safe scoped wipe (single transaction). Use the target set from Step 1 as the subquery:
    ```sql
    BEGIN;
    WITH targets AS (
      SELECT DISTINCT a.id
      FROM arguments a
      JOIN pipeline_runs pr ON pr.argument_id = a.id
      WHERE pr.strategy = 'convokit_import'
    )
    -- Order matters (FK dependencies): AdminJob first (nullable FK to argument),
    -- then leaf children, then PipelineRun, then Argument last.
    , d_jobs   AS (DELETE FROM admin_jobs           WHERE argument_id IN (SELECT id FROM targets))
    , d_utt    AS (DELETE FROM utterances           WHERE argument_id IN (SELECT id FROM targets))
    , d_part   AS (DELETE FROM argument_participants WHERE argument_id IN (SELECT id FROM targets))
    , d_calink AS (DELETE FROM case_arguments        WHERE argument_id IN (SELECT id FROM targets))
    , d_runs   AS (DELETE FROM pipeline_runs         WHERE argument_id IN (SELECT id FROM targets))
    DELETE FROM arguments WHERE id IN (SELECT id FROM targets);
    -- Verify row counts look right, then:
    COMMIT;   -- (or ROLLBACK; if anything looks wrong)
    ```
    (Confirm the real table names against api/models/models.py __tablename__ values before running; adjust if they differ. Orphaned corpus Cases may be left in place — _get_or_create_case is idempotent on re-run — or cleaned up separately if desired.)

    Step 3 — Re-run the idempotent import path (produces correct status=PIPELINE + paired AdminJob rows):
