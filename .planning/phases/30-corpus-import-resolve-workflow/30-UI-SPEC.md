# Phase 30 — UI Design Contract

> Visual and interaction contract for the Pipeline List page's corpus-vs-PDF source identification gap. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope reminder:** Phase 30 is overwhelmingly a backend/wiring phase (routing corpus-imported arguments through the existing `AdminJob` paused/resolve workflow — D-01 through D-05 in `30-CONTEXT.md`). This contract covers ONLY the one real, narrow UI gap surfaced during discuss-phase: **the Pipeline list/history table at `/admin/pipeline/` (`app/src/routes/admin/pipeline/+page.svelte`) gives an operator no way to tell a corpus-imported job apart from a PDF-ingested job**, which matters once the queue holds up to ~7,800 paused rows (D-03).

**Explicitly OUT OF SCOPE (per D-05 — do not re-litigate):**
- `ResolveCard` (`/admin/pipeline/[job_id]`) — reused **completely unchanged**. Same columns (Raw label · Resolved as · Bench/Advocate · Argument Role · Title · Action), same person re-matching affordances, same `?/resolve` batch action. This UI-SPEC does not touch it.
- `RunStatusCard` and the rest of the job detail page — unchanged.
- Any new bulk/batch-approve UI (D-04, explicitly deferred to a future phase).
- Any new filter control scoped to source (not requested; would compound the already-deferred bulk-tooling discussion — do not add).

**No new hex values introduced.** The Source tag ("PDF" / "Corpus") reuses `#94a3b8` for both border and text, on a `#0f1117` background — a background lighter/darker distinction from the adjacent status badge's `#1e293b` background is enough to visually separate the two tags without competing for the operator's attention.

**Rationale for choosing the neutral grey (not the accent blue) for the Source tag:** the compound status badge already carries the semantically important, action-driving signal (what state is this row in, does it need review). Source (PDF vs. Corpus) is provenance metadata, not an urgency signal — giving it a neutral, quiet treatment (mirroring the Phase 29 per-argument attribution note's "quiet, non-promotional" precedent) keeps the operator's eye correctly prioritizing status over origin when scanning a long list.

2. `#4ade80` (green) — "Completed" status badge only

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Not applicable — this phase adds no new primary action; existing "View" link (unchanged) remains the only per-row action |
| Empty state heading | Not applicable — existing "No runs yet" / "No jobs need attention" empty states are unchanged and unaffected by this addition |
| Empty state body | Not applicable (unchanged) |
| Error state | Not applicable — the Source tag is a pure display derived from existing job data; it has no independent failure mode (if the backend value is ever missing, default per Interaction Contract below) |
| Destructive confirmation | Not applicable — no destructive actions in this phase's UI surface |
| **Source tag — PDF-ingested job** | `"PDF"` |
| **Source tag — corpus-imported job** | `"Corpus"` |

Both tag labels are short, single-word, and use title case, matching the existing compound badge's step-label capitalization convention ("Ingest", "Parse", "Resolve").

**Why not merge into the compound status badge (e.g. "Corpus · Resolve · Needs Review")?** Confirmed against the existing `badgeLabel()` function (`+page.svelte`) — it already composes two concerns (step + status) into one string. Adding a third concern (source) to the same string produces an increasingly long, harder-to-scan label at a glance across thousands of rows, and conflates a semantic-urgency signal (status) with a provenance signal (source). Keeping Source as its own adjacent, visually distinct tag preserves the existing badge's meaning untouched and lets the operator's eye separate "what state is this in" from "where did this come from."

## Component Inventory

### 1. Source Tag (new)

**File:** `app/src/routes/admin/pipeline/+page.svelte` (new helper function + new `<td>`/`<span>` markup — no new component file needed; this is a two-value tag, not worth extracting to `$lib/components/`)

**New helper function (alongside existing `badgeStyle`/`badgeLabel`):**
```ts
// sourceTagStyle/sourceLabel: renders "PDF" or "Corpus" as a quiet, neutral tag
// distinct from the semantic-color compound status badge (Phase 30 gap closure).
function sourceLabel(source: 'pdf' | 'corpus'): string {
  return source === 'corpus' ? 'Corpus' : 'PDF';
}

function sourceTagStyle(): string {
  return `border: 1px solid #94a3b8; border-radius: 4px; padding: 2px 8px; font-size: 14px; font-weight: 400; background-color: #0f1117; color: #94a3b8; display: inline-block;`;
}
```

**Visual spec:**
- Single, static neutral style — unlike the status badge, the tag's color never changes based on value; only the text ("PDF" vs "Corpus") changes.
- No icon (matches this codebase's established no-icon-library convention).

### 2. Runs Table — new "Source" column (modified)

**File:** `app/src/routes/admin/pipeline/+page.svelte`

**Changes from current** (confirmed via direct read — current columns are `Status | Created | (View link)`, no docket/case-name/filename column exists today):

- `<th scope="col">Source</th>` — identical header cell styling to the existing `Status`/`Created` headers

## Data Contract Note (non-template — required before the Source tag can render anything real)

**This is a backend data-shape requirement the planner must account for; it is not itself a visual/interaction decision, but the Source tag above cannot be implemented without it.**

Confirmed via direct read of `api/schemas/admin_jobs.py` and `api/services/admin_jobs.py`:
- `AdminJobResponse` has **no existing field** that distinguishes a corpus-imported job from a PDF-ingested one. `pdf_url`, `spaces_key`, and `original_filename` are all `Optional` and would legitimately be `NULL` for a corpus-imported job (which never goes through `ingest`), but their absence alone is a fragile signal to build a UI contract on (a future PDF-ingest edge case could also leave them null).
- The existing, already-shipped precedent for this exact kind of derived-flag problem is `list_jobs()`'s `is_archived` computation (Phase 26 gap closure, `admin_jobs.py:219-255`): it `outerjoin`s `Argument` on `AdminJob.argument_id == Argument.id` and derives a boolean at read time, injected via `job.__dict__["is_archived"] = ...` before Pydantic serialization.
- **Recommended approach (for the planner to confirm/adjust during planning, not locked here):** add a `source: Literal["pdf", "corpus"]` field to `AdminJobResponse`, derived in `list_jobs()` (and `get_job()`, for consistency) by checking whether the job's linked `Argument` has any associated `PipelineRun` with `strategy == "convokit_import"` (the exact strategy string Phase 29 already stamps on every corpus-imported argument's `PipelineRun` row — see `pipeline/commands/import_convokit.py`'s `PIPELINE_RUN_STRATEGY` constant). Default to `"pdf"` when no such `PipelineRun` exists, matching the "absence implies the ordinary path" convention already used for `is_archived`.
- This mirrors an already-established, shipped pattern (outerjoin + derived field, no schema/migration needed) — it is a query-shape decision, not a new column, consistent with `30-CONTEXT.md`'s note that "no schema changes anticipated" for this phase.
