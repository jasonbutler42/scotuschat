# Phase 30.1 Plan 03: Question number nullable column + endpoint hardening Summary

**Migration 0019 makes arguments.question_number nullable (parity with argued_date); admin router now catches IntegrityError as a 409 instead of leaking a 500; CaseItem/ArgumentMetadataResponse schemas accept None**

## Performance

## Accomplishments
- Closed the AEDIT-04 / UAT test 3 gap: blanking the Question number field in the Argument Details card and saving no longer raises an unhandled 500 — `arguments.question_number` is now a nullable column with no server default (migration 0019), matching `argued_date`'s existing nullable-column precedent (migration 0011)
- Hardened `PATCH /api/admin/arguments/{id}/metadata` with a dedicated `except IntegrityError` clause (session rollback + generic 409 `"constraint_violation"` detail) as defense-in-depth against any future NOT NULL/constraint mismatch, without leaking raw DB/asyncpg messages (T-30.1-06)
- `CaseItem` and `ArgumentMetadataResponse` schemas both updated to `question_number: int | None = None`, mirroring the argued_date Optional-over-nullable-column pattern already used one field above each
- Added `api/tests/test_question_number_nullable.py` (TDD RED -> GREEN), a pure-Python, no-DB regression test mirroring `test_case_item_argued_date_optional.py`'s style — safe against the known shared-dev-DB test-leak issue (999.19)

## Files Created/Modified
- `alembic/versions/0019_question_number_nullable.py` - New migration: alter_column nullable=True, server_default=None on arguments.question_number; downgrade backfills NULL->1 before re-tightening (mirrors migration 0011)
- `api/models/models.py` - Argument.question_number changed from `nullable=False, default=1` to `nullable=True` (no default), matching the migrated DB column
- `api/routers/admin.py` - Imported `sqlalchemy.exc.IntegrityError`; `update_argument_metadata` now has a separate `except IntegrityError` clause (rollback + 409 `"constraint_violation"`), independent of the existing `except ValueError` -> 422 path
- `api/schemas/cases.py` - `CaseItem.question_number` changed from required `int` to `int | None = None`
- `api/schemas/utterance.py` - `ArgumentMetadataResponse.question_number` changed from required `int` to `int | None = None`
- `api/tests/test_question_number_nullable.py` - New regression test: CaseItem/ArgumentMetadataResponse accept `question_number=None`; source-assertion that `admin.py` references `IntegrityError`

## Decisions Made
- Confirmed product decision (2026-07-11, not re-opened by this plan): blank `question_number` means NULL / "unknown", full parity with `argued_date`. No client-side block; DB-level allow-NULL.
- IntegrityError handling is defense-in-depth only — after migration 0019 the diagnosed blank-question_number path no longer raises IntegrityError at all, but the router now degrades any future NOT NULL/constraint violation to a clean 409 instead of an unhandled 500.
- `api/services/arguments.py:37`'s docstring (return-dict shape comment, not a type annotation) was left unchanged — it doesn't explicitly claim a non-null int and already passes `argument.question_number` through with no coercion, consistent with how the identical `argued_date` docstring line was left unchanged in the earlier 29-07 gap fix.
