# Phase 30.1: Close gap: AEDIT-04/DASH-02 — wire ArgumentDetailsCard + status filter into arguments admin page - Context

**Gathered:** 2026-07-11
**Status:** Ready for planning

<domain>
## Phase Boundary

Close two confirmed cross-phase integration gaps found by `/gsd-audit-milestone v1.5` (see `.planning/v1.5-MILESTONE-AUDIT.md`):

1. **AEDIT-04:** `/admin/arguments/[id]` currently hand-rolls its own Argument Details form instead of consuming the shared `ArgumentDetailsCard.svelte` component that Phase 23 built and Phase 25 already reuses on the pipeline job detail page. This phase makes `/admin/arguments/[id]` an actual second consumer of that component.
2. **DASH-02:** The dashboard's three status CTAs link to `/admin/arguments?status=draft|published|unpublished`, but no layer (frontend `load()`, FastAPI router, or service function) reads that query param — the list always renders unfiltered. This phase wires the param through end-to-end.

Both gaps touch overlapping code in the same route (`/admin/arguments/`), which is why they were combined into one closure phase rather than two.

This phase does NOT touch People Admin, Pipeline pages, or add any new capability beyond making these two already-"Complete" requirements actually true end-to-end.

</domain>

<decisions>
## Implementation Decisions

### AEDIT-04 — Docket data reconciliation (the crux decision)
- **D-01:** `ArgumentDetailsCard`'s pill editor binds to `Argument.source_docket` / `Argument.source_dockets` (the pipeline ingest-tracking array — same field the component already edits on the pipeline job detail page), **not** `Case.docket_number`. This is the smallest-change option and matches the component exactly as Phase 23 built it.
- **D-02 (direct consequence of D-01):** The **real case docket number** (`Case.docket_number`, the lead case's actual docket — what's in the public URL/slug) is a genuinely different field from `source_dockets` and is NOT edited by the shared card. It stays exactly as it is today: a separate plain-text field, unchanged, alongside the read-only `consolidated_dockets` list (other `Case` rows joined via `CaseArgument`). No new Case/CaseArgument row CRUD is introduced by this phase — that would be a much larger lift than this gap-closure phase scopes to.
- **D-03 (layout, resolves D-01/D-02 + case title placement together):** `argued_date` moves out of the old hand-rolled form and into the new `ArgumentDetailsCard` (the component already owns `argued_date`). The old form is reduced to a small separate **"Case" card**: case title (`case_name`) + real docket number (`Case.docket_number`) + read-only consolidated dockets, keeping its existing `?/save` action and behavior completely unchanged. `ArgumentDetailsCard` becomes a second, separate card on the page — source_dockets pills + question number (net-new editable field on this page — was never exposed here before) + argued date + hints — laid out exactly like the pipeline job detail page's card. **Do not attempt to merge `case_name` into the shared component** — it was never designed to hold it (confirmed: no `case_name` field in `ArgumentDetailsCard`'s props).
- **D-04:** `ArgumentDetailsCard`'s always-visible "Extracted: X" hint rows (sourced from `Argument.cover_metadata`) DO show on this page, unmodified — same behavior as the pipeline job detail page, no new `showHints`-style suppression prop. Provenance info ("this value came from the PDF") is treated as harmless/useful even after the argument is resolved and published, consistent with the project's transparency-by-default pattern.

### DASH-02 — Status filter wiring
- **D-05:** The arguments list page (`/admin/arguments`) gets a **visible filter control with an active-filter indicator** once `?status=` is wired through — not a silent pass-through. Precedent: Phase 27's People page already establishes visible active-filter state + click-to-change on this exact admin surface. Concretely this needs at minimum: something showing "Showing: Draft" (or equivalent) plus a way to clear back to the full list — exact visual form (segmented buttons vs. dropdown vs. pill row) is Claude's discretion (see below).
- **D-06:** The fix threads `status` from `+page.server.ts` → FastAPI router (`GET /api/admin/arguments`) → `admin_arguments.list_arguments(db, status=...)`, per the milestone audit's own recommendation — contained to these 3 files, no migration needed.

### Claude's Discretion
- Exact visual treatment of the new filter control (D-05) — segmented Draft/Published/Unpublished/All buttons, a `<select>`, or filter-pill row — pick whatever best matches the existing admin dark-theme card/button conventions already established on this page and on `/admin/people`.
- Behavior when `?status=` is present but invalid/unrecognized — default to showing the full unfiltered list (today's behavior), no error state needed.
- Whether the new "Case" card (D-03) is laid out above or below the new `ArgumentDetailsCard` — no strong preference surfaced; follow whatever reads best given Status/Status history/Speakers card ordering already on the page.
- Exact copy for the active-filter indicator (D-05) — e.g. "Showing: Draft arguments" vs. "Filtered by status: Draft" — pick clear, non-alarmist copy consistent with the project's established admin tone.

</decisions>

<specifics>
## Specific Ideas

- The docket-data mismatch (D-01/D-02) is the single most important thing downstream agents must not get wrong: `Argument.source_dockets` (pipeline ingest-tracking) and `Case.docket_number` (real case identity, via `CaseArgument`) are two distinct fields that happen to both be called "docket" in casual conversation. The milestone audit's fix recommendation ("contained to 1-2 files") did not account for this distinction — research/planning should treat the audit's estimate with caution and re-scope based on the actual decision locked here (D-01: bind the card to `source_dockets`, leave `Case.docket_number` untouched in its own small card).
- Filter visibility (D-05) should feel like the same design language as Phase 27's People page filters — not a new, different filter idiom.

</specifics>
