# Phase 30.1: Code Review Report

**Reviewed:** 2026-07-11
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

Reviewed the DASH-02 (status filter on `/admin/arguments`) and AEDIT-04 (`ArgumentDetailsCard` second-consumer) wiring against the phase plans (`30.1-01-PLAN.md`, `30.1-02-PLAN.md`) and against the full contents of the seven listed files. The two pieces of new wiring themselves are implemented correctly and match their plans: the `status` query param is validated with an allow-list before ever touching `ArgumentStatusEnum()` (no injection risk), and the `saveArgumentDetails` action correctly omits `case_name` and derives the argument id solely from `params.id` (no IDOR).

However, the new wiring exposes/introduces four real defects:

1. A pre-existing, un-caught `ValueError` in `update_argument_metadata`'s date parsing is now reachable through a brand-new write path (`ArgumentDetailsCard` → `saveArgumentDetails` → `PATCH /arguments/{id}/metadata`) and returns an unhandled 500 instead of a controlled 422, unlike its sibling `PATCH /arguments/{id}` route.
2. The same endpoint silently no-ops when an operator tries to *clear* `question_number` or `argued_date` (or enters a non-numeric `question_number`), while the UI still reports "Saved." — a false-positive success message.
3. The new list-page status filter is lost (and publish/unpublish failures are silently swallowed) by the pre-existing `publish`/`unpublish` actions on `/admin/arguments`, which unconditionally redirect to the bare, unfiltered URL.
4. The new DB-level filtering behavior (`status=draft|published|unpublished` actually narrowing results) has no test coverage — only route-resolution/auth is tested.

## Narrative Findings (AI reviewer)

### CR-01: Malformed `argued_date` in the new metadata write path returns an unhandled 500 instead of a 422

**File:** `api/routers/admin.py:1086-1104`
**Issue:** `update_argument_metadata()` (the service function backing the route) re-raises `ValueError("invalid_date_format")` when `datetime.date.fromisoformat(body.argued_date)` fails (`api/services/admin_arguments.py:826-832`):

```python
if body.argued_date:
    try:
        parsed_date = datetime.date.fromisoformat(body.argued_date)
    except ValueError:
        raise ValueError("invalid_date_format")
```

The route that calls it does **not** catch `ValueError`:

```python
@router.patch("/arguments/{argument_id}/metadata")
async def update_argument_metadata(
    argument_id: int,
    body: MetadataUpdate,
    db: AsyncSession = Depends(get_db),
) -> dict:
    result = await arguments_service.update_argument_metadata(db, argument_id, body)
    if result is False:
        raise HTTPException(status_code=404, detail="Argument not found")
    return {"success": True}
```

Compare this to the sibling `PATCH /arguments/{argument_id}` route (`api/routers/admin.py:1035-1038`), which wraps the identical `update_argument()` call in `try/except ValueError: raise HTTPException(422, ...)`. This endpoint is now the write path for the new `saveArgumentDetails` action added in this phase (`app/src/routes/admin/arguments/[id]/+page.server.ts:223-252`) — any malformed `argued_date` string reaching the API directly (bypassing the `<input type="date">` browser guard — e.g. a scripted/replayed request, or a future non-browser caller) will produce an uncaught exception and a bare 500 response rather than a handled 422. The SvelteKit action happens to treat any non-2xx as `fail(422, {...})`, which masks the symptom client-side, but the server-side defect (unhandled exception on attacker/operator-controlled input) is real and inconsistent with the rest of this file's error-handling convention.

**Fix:**
```python
@router.patch("/arguments/{argument_id}/metadata")
async def update_argument_metadata(
    argument_id: int,
    body: MetadataUpdate,
    db: AsyncSession = Depends(get_db),
) -> dict:
    try:
        result = await arguments_service.update_argument_metadata(db, argument_id, body)
    except ValueError as exc:
        raise HTTPException(status_code=422, detail=str(exc)) from exc
    if result is False:
        raise HTTPException(status_code=404, detail="Argument not found")
    return {"success": True}
```

## Warnings

### WR-01: Clearing `question_number` / `argued_date` (or an invalid `question_number`) silently no-ops while the UI reports "Saved."

**File:** `api/services/admin_arguments.py:826-862` (reached via `app/src/routes/admin/arguments/[id]/+page.server.ts:223-252`)
**Issue:** The new `saveArgumentDetails` action sends `argued_date: argued_date` where `argued_date` is `null` when the operator blanks the date field, and `question_number: question_number || null` where blanking the field also produces `null`. In `update_argument_metadata`:

```python
parsed_date: datetime.date | None = None
if body.argued_date:                      # None/'' → skipped, no update issued
    try:
        parsed_date = datetime.date.fromisoformat(body.argued_date)
    except ValueError:
        raise ValueError("invalid_date_format")
...
if parsed_date is not None:
    values_to_set["argued_date"] = parsed_date
...
if body.question_number is not None and body.question_number.strip():
    try:
        values_to_set["question_number"] = int(body.question_number)
    except ValueError:
        pass  # non-numeric silently skipped
```

There is no `else` branch that writes `NULL` when the operator intentionally clears these fields — unlike `source_dockets`, which the same function *does* correctly NULL out on an empty list (`values_to_set["source_dockets"] = normalized if normalized else None`). The result: an operator who blanks `argued_date` or `question_number` on the `ArgumentDetailsCard` and clicks "Save Argument Details" gets the component's "Saved." success message, but the value is silently left unchanged in the database — an inconsistent, false-positive success state. The same silent-skip applies to a non-numeric `question_number` (e.g. a stray "N/A" pasted from a hint).
**Fix:** Distinguish "field omitted" from "field explicitly cleared" at the schema/action boundary, and write `NULL` explicitly when cleared — e.g. have the frontend send an explicit sentinel (or always include the keys) and update the service:
```python
if "argued_date" in provided_fields:
    values_to_set["argued_date"] = (
        datetime.date.fromisoformat(body.argued_date) if body.argued_date else None
    )
```
At minimum, surface a validation/error message to the operator (instead of "Saved.") when a non-empty `question_number` fails `int()` parsing, so the silent-skip isn't reported as success.

### WR-02: List-page publish/unpublish actions drop the new `?status=` filter and swallow failures silently

**File:** `app/src/routes/admin/arguments/+page.server.ts:53-89`
**Issue:** Both actions always redirect to the bare, unfiltered list regardless of outcome:

```ts
publish: async ({ request, fetch }) => {
    const formData = await request.formData();
    const argument_id = formData.get('argument_id') as string;
    try {
        const res = await fetch(`${FASTAPI_BASE_URL}/api/admin/arguments/${argument_id}/publish`, {
            method: 'POST',
            headers: { 'X-Admin-Token': ADMIN_TOKEN },
        });
        if (!res.ok) {
            console.error('[arguments publish] FastAPI returned', res.status, await res.text());
        }
    } catch (err) {
        console.error('[arguments publish] fetch threw:', ...);
    }
    throw redirect(303, '/admin/arguments');   // always, even on failure
},
```

Two problems, both directly relevant to this phase's new DASH-02 filter feature:
1. **Filter loss:** An operator viewing `/admin/arguments?status=draft` who clicks "Publish" on a row is redirected to `/admin/arguments` (no `status`), silently dropping the filter they set — the new segmented control state does not survive the very row-action it's meant to coexist with.
2. **Silent failure:** If the publish/unpublish `fetch` fails (e.g. 422 because `resolved_at` is null, or a network error), the only signal is a server-side `console.error` — the redirect still fires as if it succeeded, and the operator sees no error message anywhere in the UI.

**Fix:** Preserve the referring filter and surface failures, e.g.:
```ts
publish: async ({ request, fetch, url }) => {
    const formData = await request.formData();
    const argument_id = formData.get('argument_id') as string;
    const status = url.searchParams.get('status');
    const target = status ? `/admin/arguments?status=${status}` : '/admin/arguments';

    let res: Response;
    try {
        res = await fetch(`${FASTAPI_BASE_URL}/api/admin/arguments/${argument_id}/publish`, {
            method: 'POST',
            headers: { 'X-Admin-Token': ADMIN_TOKEN },
        });
    } catch (err) {
        return fail(502, { publishError: 'Could not publish. Try again.' });
    }
    if (!res.ok) {
        return fail(422, { publishError: 'Could not publish. Try again.' });
    }
    throw redirect(303, target);
},
```
(mirror for `unpublish`).

### WR-03: No test verifies the `status` filter actually narrows results at the DB layer

**File:** `api/tests/test_admin_arguments_routes.py`
**Issue:** `test_list_arguments_status_param_route_resolution_returns_401_not_422` only proves the route accepts the `status` query param and that auth fires first (401, not 422). No test — DB-guarded or otherwise — asserts that `GET /api/admin/arguments?status=draft` actually returns only DRAFT rows, or that `?status=bogus` returns the unfiltered full list. A future regression in the `list_arguments()` allow-list/where-clause logic (the core DASH-02 behavior) would not be caught by this test suite.
**Fix:** Add a `_db_configured()`-gated, read-only test that seeds (or reuses) rows of each status and asserts the returned `argument_id`s for `?status=draft` / `?status=published` / `?status=unpublished` / `?status=bogus` match expectations, following the existing pattern used elsewhere in this file for DB-guarded tests.

## Info

### IN-01: Page-wide `form` object is implicitly shared across six unrelated form actions

**File:** `app/src/routes/admin/arguments/[id]/+page.svelte:5, 246-252`; `app/src/routes/admin/arguments/[id]/+page.server.ts` (all actions)
**Issue:** SvelteKit's single `form` prop is populated by whichever of `save`, `saveArgumentDetails`, `publish`, `unpublish`, `delete`, or `updateParticipantSide` last ran, and the same `form` object is passed straight into `<ArgumentDetailsCard {form} />` (which only reads `form.saved`/`form.saveError`/`form.dockets`). Today this is safe only because every action happens to use a distinct key name (`error`, `saveError`, `roleError`, `deleteError`, `saved`). There's no compile-time or runtime guard preventing a future action from reusing one of `ArgumentDetailsCard`'s expected keys (e.g. `saved`/`dockets`), which would cause it to render a spurious "Saved." message or reseed docket pills from unrelated form state.
**Fix:** Consider namespacing action results (e.g. `{ saveArgumentDetails: { saved: true } }`) or adding a short code comment at the top of the actions object documenting the "keys must never collide across actions" invariant this design currently relies on.
