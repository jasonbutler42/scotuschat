# Phase 40.1: Sanitize docket input to close path-traversal/arbitrary-file-write gap - Context

**Gathered:** 2026-07-29
**Status:** Ready for planning

<domain>
## Phase Boundary

Close the confirmed path-traversal / arbitrary-file-write vulnerability in the docket-input data flow: an admin-authenticated operator can enter a docket value (via `DocketPillInput` on the Pipeline Runner new-job form) containing `../` segments, an absolute path, or filesystem-illegal characters, which then flows unsanitized through `+page.server.ts` → FastAPI `POST /api/admin/jobs` → the spawned ingest subprocess → `pipeline/commands/ingest.py:291`, where it is f-string interpolated directly into a PDF filename and joined onto `Path("data/pdfs")` with zero sanitization. This phase adds sanitization/validation to close that gap. It does not add real SCOTUS docket-format enforcement (e.g. requiring `"22-915"` shape) — see Decisions below.

</domain>

<decisions>
## Implementation Decisions

### Validation strategy
- **D-01:** Use permissive sanitization, not a strict docket-shape allow-list. Strip/reject filesystem-dangerous characters and sequences — path separators (`/`, `\`), `..` traversal segments, a leading absolute-path indicator (POSIX leading `/`, Windows drive letter like `C:`), double/single quotes, control characters, and null bytes — but otherwise permit free text. Do not require the strict `\d{1,2}-\d+` docket-number shape (that existing `DOCKET_RE` pattern in `cover_extractor.py` is scoped to parsing PDF cover-page text and is explicitly out of scope for this fix per user decision). — **Reversibility:** reversible — a future phase can tighten this to a strict allow-list without breaking existing valid data, since anything currently accepted under permissive sanitization remains a superset-safe input.
- **D-02:** Applies to every docket-shaped input in the flow: both `primary_docket` (legacy single-docket field) and every entry in the `source_dockets` list (Phase 24 Plan 04 multi-docket/consolidated-case support) — not just the primary docket. Confirmed via `api/routers/admin.py` `_normalize_dockets` that both fields ultimately feed the same ingest filename-construction path.

### Enforcement layers
- **D-03:** Defense-in-depth — implement sanitization/rejection at two hard boundaries, not just one:
  1. **FastAPI Pydantic layer** (`create_job` route, `api/routers/admin.py`): add a `Field` pattern/validator on `primary_docket` and each `source_dockets` entry, following the existing precedent set by `ResolveRowUpdate.title` (`Field(default=None, max_length=500)`) which the codebase already documents as the pattern for turning unhandled DB/OS errors into a proper 422 validation response.
  2. **`pipeline/commands/ingest.py`** immediately before the filename is constructed (line ~291): add a hard sanitizer/guard as a last line of defense, so the fix holds even if a future caller reaches ingest.py without going through the FastAPI route (e.g. a direct CLI invocation, which is a legitimate operator-facing use case per this project's "pipeline is offline-CLI" architecture rule in CLAUDE.md).
  - Optional/nice-to-have, not required: mirror lightweight client-side feedback in `DocketPillInput.svelte` for faster UX (reject-on-type), but the two backend boundaries above are the actual security fix and must not be skipped even if frontend mirroring is deferred. — **Reversibility:** costly — removing either backend boundary later would require re-auditing every docket-input call site found by the original debug session (`DocketPillInput.svelte` → `+page.server.ts` → `create_job` → `_normalize_dockets` → ingest subprocess argv → `ingest.py:291`) to confirm no regression.
- **D-04:** The existing `_normalize_dockets` leading-`"-"` rejection (T-24-08, CLI argv-flag-injection guard) is a different threat class and must be preserved unchanged — this phase adds filesystem-path/character-shape safety alongside it, not instead of it.

### Claude's Discretion
- Exact character allow/deny-list implementation detail (regex vs. explicit blocklist of dangerous characters) and whether to centralize the sanitizer as a shared utility function (recommended, since the debug session's evidence flagged `ingest.py:291` as the sole current filesystem-path call site but noted "the fix should still land as a shared/reusable sanitizer... in case future call sites are added").
- Exact FastAPI error response shape for a rejected docket (should follow the existing 422/409 structured-error pattern already used elsewhere in `admin.py`, not a new ad hoc shape).
- Whether/how to add a regression test that reproduces the original traversal experiment (`Path("data/pdfs") / "../../../tmp/evil-q1.pdf"` and the absolute-path-override case) as an automated test.

</decisions>

<specifics>
## Specific Ideas

No specific UI/UX examples given — this is a backend security fix. The debug session's own pathlib experiments (documented in `.planning/debug/docket-filename-injection.md`) are the concrete reproduction cases the fix must close:
- `Path("data/pdfs") / "../../../tmp/evil-q1.pdf"` must no longer escape `data/pdfs/`.
- `Path("data/pdfs") / "/etc/cron.d/evil-q1.pdf"` (absolute-path override) must no longer discard the base directory.
- A double-quote character (the original crash trigger, UAT Test 6 Phase 38) must be rejected/sanitized rather than causing `[Errno 22] Invalid argument`.

</specifics>
