## Layout & Placement Contract

- New section is the **last** section on `/admin`, placed after the existing "Web Traffic" placeholder, with `margin-top: 48px` (matches the existing gap between the stat-card grid and Web Traffic).
- Outer container: same card treatment as every other section on the page — `background-color: #1e293b; border: 1px solid #334155; border-radius: 8px; padding: 24px;`. Do **not** give this section a red-tinted border or red background tint — the established "Danger Zone" precedent (both entity-detail pages) keeps the outer card neutral and puts all destructive signaling into the heading badge, button, and copy, not the container. Deviating from that here would be visual noise inconsistent with the rest of the codebase.
- Section heading: `<h2>` "Dev Tools" at the same style as every other section heading (`font-size: 20px; font-weight: 600; color: #e2e8f0; margin: 0 0 16px 0; line-height: 1.2;`), with a small warning-colored badge immediately after it reading "DEV ONLY" (see Badge spec below). The badge exists because, unlike the per-entity Danger Zone sections, this one is not just destructive — it must not be mistaken for a normal operator workflow action.
- Inside the section: one sub-block for "Reset to Fixture" (this phase's only control; no other dev tools exist yet, so no internal sub-headings are needed — the section heading and description together are sufficient).
- This entire section is **structurally absent** from the rendered page outside development environments (D-07) — not hidden, not disabled, not rendered-then-CSS-hidden. There is no "disabled in production" visual state to design because the section never reaches the DOM. See UI Considerations below.

### "DEV ONLY" badge spec

Reuses the exact `StatusBadge` convention from `pipeline/[job_id]/+page.svelte` (border + text on card surface, never filled):

```
display: inline-flex; align-items: center; gap: 4px;
border: 1px solid #fbbf24; border-radius: 4px; padding: 2px 8px;
font-size: 14px; font-weight: 400; color: #fbbf24; background-color: #1e293b;
margin-left: 8px; vertical-align: middle;
```

## Interaction & State Contract — "Reset to Fixture"

Five states, driving one control. Modeled directly on the two existing "Danger Zone" delete precedents (two-step inline confirm, no modal/overlay), extended with a running/success state since this action is multi-step (TRUNCATE + 4× reseed import + 2× state-transition service calls) rather than a single-row delete.

### 1. Idle (default)
- Description copy (14px, `#94a3b8`) above the button, always visible in every state: "Wipes every argument, utterance, person, court tenure, and participant in this database, then reseeds exactly the four confirmed fixtures (see FIXTURES.md) through the corpus importer."
- Button: full-width, `min-height: 44px`, `background: transparent; border: 1px solid #ef4444; border-radius: 6px; font-size: 16px; font-weight: 600; color: #ef4444;` — label "Reset to Fixture". Identical styling to "Delete argument"/"Delete run".

### 2. Confirming
- Clicking the Idle button does **not** submit anything — it swaps the button for a confirmation block in place (no layout shift beyond the block growing downward), matching the established `deleteConfirming` pattern.
- Confirmation block, in order:
  1. A statement of exactly what will be wiped (success criterion 3) — copy: "This will permanently delete **every** argument, utterance, person, court tenure, and participant record — not just the fixtures. It cannot be undone." Rendered at 16px, `#e2e8f0`, with the word "every" as the only emphasized (bold) span — no color change, weight only.
  2. Two-button row directly below, `display: flex; gap: 8px;`, each button `flex: 1; min-height: 44px;`:
     - "Confirm reset" — `border: 1px solid #ef4444; color: #ef4444; background: transparent; font-weight: 600;` (same visual weight as "Confirm delete")
     - "Cancel" — `border: 1px solid #334155; color: #94a3b8; background: transparent; font-weight: 400;`

### 3. Running
- On "Confirm reset" click, the two-button row is replaced in place (same row height, no shift) by a single status line: animated spinner glyph (`◌`, `animation: spin 1s linear infinite`) + text "Resetting to fixture…" at 16px `#94a3b8`.
- No progress bar / step-by-step breakdown — success criteria don't require it and no existing precedent in this codebase shows granular multi-step progress for a synchronous action (the job-polling UI is a different, heavier pattern reserved for real background pipeline runs). If the underlying implementation turns out to need a background job instead of a blocking request, the polling/spinner visual is the same either way from the UI's perspective — this is a note for planning, not a UI-SPEC blocker.
- All controls in this section are non-interactive while Running (no double-submit).

### 4. Success
- Replaces the status line with a success indicator reusing the `completed` StatusBadge convention: `border: 1px solid #4ade80; color: #4ade80; background-color: #1e293b;` badge reading "✓ Reset complete", followed by a plain-text list (16px `#e2e8f0`, one per line) of the four reseeded fixtures by case name + role, e.g.:
  - "Baltimore & Ohio Railroad Co. v. United States — Complexity fixture"
  - "[Draft-target case name] — Draft"
  - "[Published-target case name] — Published"
  - "[Mid-pipeline-target case name] — Mid-pipeline"
  (Exact case names come from `.planning/FIXTURES.md`; planner/executor fill these from that file, not from this spec.)
- Per success criterion 1/4, the rest of the `/admin` page (Needs Attention section, stat-card grid) must reflect the post-reset counts without a manual browser refresh — the success handler must trigger a reload of the page's load-function data (e.g. `invalidateAll()` or the same `await update()` pattern the two delete precedents already use), not just locally patch this section's own state.
- The "Reset to Fixture" button returns to its Idle state below/after this success block so the operator can run it again without reloading the page.

### 5. Error
- Same visual treatment as the existing `form?.deleteError` precedent: `role="alert"`, `color: #ef4444; font-size: 14px; font-weight: 400; margin: 8px 0 0 0;`, positioned directly below where the button/status row was.
- Two distinct error copies (see Copywriting Contract) depending on failure type — a mid-reset failure is a materially different (and more alarming) situation than a same-request refusal, and the copy must not paper over that difference.
- After an error, the control returns to Idle (not Confirming) — the operator must explicitly re-trigger and re-confirm rather than being dropped back into a pre-armed confirm state.

## UI Considerations

| Category | Element(s) | Status | Resolution / Reason |
