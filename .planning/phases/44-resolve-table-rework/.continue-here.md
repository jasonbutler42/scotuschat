## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| WSL/Windows network split | A process started via plain WSL bash and a process started via `powershell.exe` live in different network namespaces and cannot reach each other over `localhost`, even though both appear to be "running". | blocking | Always launch both dev servers as native Windows processes via `powershell.exe -NoProfile -Command "Start-Process ..."`; verify with `Invoke-WebRequest` via `powershell.exe`, never `curl` from WSL. |
| Ambiguous `side='UNKNOWN'` | `ArgumentParticipant.side` defaults to `SideEnum.UNKNOWN` at the DB level, AND an operator's own "confirm generic Advocate, no specific role yet" action (`confirmSide`) also writes the literal string `'UNKNOWN'`. There is no way to distinguish "never touched" from "explicitly confirmed as generic advocate" from the stored value alone. | advisory | Any new logic that gates on `side` must treat this ambiguity as unresolvable from `side` alone — look for a second signal (e.g. `person_id != null`) before treating `UNKNOWN` as confirmed. See `sideGateConfirmed`'s seeding logic in commit `2be6f8aa` for the established pattern. |
| Two-phase person matching | A person pick in the Resolved-As dropdown (`rowMatchStates[label].personId`) is CLIENT-SIDE ONLY — it does not write to `ArgumentParticipant.person_id` until the batch `?/resolve` submission commits all rows at once. Anything reading `row.person_id` / `row.bench_role` / `row.missing_tenure` (server props) will not reflect a live, uncommitted pick. | advisory | This is the exact reason the tenure-preview feature is needed — do not try to "fix" it by prematurely committing `person_id` per-row (a much bigger architecture change than intended here); build a preview endpoint instead. |
| Untyped `discrepancies` JSON | `AdminJob.discrepancies` is `Optional[list[dict]]` with no Pydantic sub-schema and no DB-level JSON schema — new keys can be added to pipeline-built discrepancy dicts with zero migration. But `pipeline/tests/test_import_convokit_adminjob.py` has an exact `set(d.keys()) == expected_keys` assertion that WILL break the moment a new key is added there, and must be updated in the same change. | advisory | When adding a new field to a discrepancy dict, grep for `expected_keys`/`set(d.keys())` in the test suite before considering the change done. |

_Remove rows that do not apply. The discuss-phase and execute-phase workflows parse this table and enforce a mandatory understanding check for any `blocking` rows._
