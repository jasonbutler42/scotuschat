<objective>
Replace the single overloaded `<select name="side">` with the two controls SEED-001's mockup
specifies: a two-button segmented Bench/Advocate toggle (which also absorbs the pre-resolution
side gate, D-07), and a real writable Argument Role dropdown for advocate rows that keeps a lock
affordance and the tenure-derived value for bench rows.

Purpose: this is the phase's actual point. Today the operator cannot say "this speaker is
Petitioner's Counsel" directly — they work through one dropdown that conflates the coarse category
with the advocate role. Both new controls write the same single stored field
(`ArgumentParticipant.side` — CONTEXT.md confirmed `argument_role` is a read-time projection of it),
so the load-bearing risk here is not the backend but the form wiring: two visual controls, one
submitted value. That gets solved once, explicitly, with a single always-present hidden `side` input
and a synchronous state flush before submit — which also closes a latent defect where the existing
gate path submitted with no side at all.

Output: a segmented toggle with exactly one active segment, a four-option Argument Role dropdown, a
lock affordance on locked bench rows, and the missing-tenure warning still visibly distinct.

Decisions implemented (CONTEXT.md):
- D-01: the Argument Role dropdown carries three real selectable roles — Petitioner's Counsel, Respondent's Counsel and Amicus Curiae — not just the two the mockup happens to show, because amicus rows exist in real transcripts and `SideEnum.AMICUS` is already fully supported — Task 2.
- D-02: a row at `UNKNOWN` or at legacy `ADVOCATE` shows an unset placeholder reading `Select case role` (the operator's exact wording, overriding the mockup's shorter literal), and saving without a pick leaves the side unchanged — Task 2.
- D-07: the pre-resolution side gate reuses this same segmented toggle with neither segment active, rather than a visually distinct pair of gate buttons — Task 1.
</objective>

Two things change together, and they must change together: the visual control, and which element
actually submits the side value.

**Single submitting control.** Add `<input type="hidden" name="side" value={effectiveSide(row)} />`
to the always-rendered per-row hidden `<form>`, immediately after the existing participant-id hidden
input. This is now the ONLY element in the row's form carrying that name. Remove the `name` and
`form` attributes from the control the Bench/Advocate cell renders — the new toggle buttons carry
neither, and neither will the Argument Role select added in Task 2. Both visual controls become pure
state mutators.

This is the Phase 27 CR-01/CR-02 fix applied to `side`. Today the gate branch renders no
side-carrying control at all, so a gate click submits a form whose `side` is absent and the
SvelteKit action rejects it with a 400 — a latent defect the always-present hidden input removes.
Note it in the SUMMARY as a fixed defect, not as new behaviour.

**Flush before submit.** Import `flushSync` from `svelte` and call it as the first statement of
`submitRow`, before `requestSubmit()`. Svelte 5 batches `$state` writes into a microtask, so setting
`pendingSideOverrides` and then synchronously calling `requestSubmit()` serializes the *previous*
hidden-input value. `flushSync()` forces the pending update into the DOM first. If `flushSync` turns
out to interact badly with the existing `rowMatchStates` effect, the documented fallback is to bind
each row's hidden input element and assign its `.value` imperatively before `requestSubmit()` —
do not instead reintroduce a named control inside the cell.

**The toggle.** Add `{#snippet sideToggle(row: MergedRow, side: string, gated: boolean, rowEditable: boolean, saving: boolean)}`
rendering one joined pill: an outer `<div role="group">` with an `aria-label` naming the row's raw
speaker label, styled `display: inline-flex; border: 1px solid #334155; border-radius: 6px;
overflow: hidden; min-height: 36px;`. Inside it, two `<button type="button">` segments, the first
carrying `border-right: 1px solid #334155` as the seam, each `font-size: 14px; padding: 6px 14px;
border: none; line-height: 1.4;`.

Derive activity as: Bench active when not gated and the effective side is `BENCH`; Advocate active
when not gated and the effective side is anything other than `BENCH` (covering `PETITIONER`,
`RESPONDENT`, `AMICUS`, `UNKNOWN`, and legacy `ADVOCATE`). When gated, neither is active — that is

otherwise `cursor: pointer;`. Set `aria-pressed` on each segment to its own active flag. Labels are
exactly `Bench` and `Advocate`.

return immediately when the requested choice is already the active one (no state write, no submit —
this is what stops a second Advocate click from resetting a stored `PETITIONER` back to `UNKNOWN`);

Introduce no new colour, font size, or font weight beyond the UI-SPEC tables. Do not touch the
Argument Role or Descriptor cells in this task.
