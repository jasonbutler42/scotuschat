<planner_deviations>
Two verified source facts contradict the phase's own upstream documents. **Source wins; do not "fix" the code back toward the doc.**

1. **Service functions own the commit in this codebase.** `49-RESEARCH.md` Pattern 3 and `49-PATTERNS.md` both state "the caller commits — the function itself never calls `db.commit()`." Direct inspection contradicts this: `api/services/admin_arguments.py::publish_argument` ends with `await db.commit()` (line 701), and so do `update_participant_side` (787), `unpublish_argument` (829), `update_argument` (598), and `admin_jobs.py::update_resolve_row_for_job`. The real rule is: **one public service entry point commits exactly once at the end; every helper it composes must NOT commit.** Follow that. `recompute_argument_tier` correctly never commits and stays that way.

2. **Migration split into 0028 + 0029.** RESEARCH recommends landing everything in one migration. Doing so would drop `people.name_needs_review` before its ~20 consumers (schemas, services, four SvelteKit files, two pipeline commands, five test modules) are updated, leaving the repo broken between plans. This plan ships `0028` (enum + participant columns + `value_discrepancy` table); plan 49-02 ships `0029` (the `people` column swap) together with every consumer, so each migration is atomic with the code that depends on it.
</planner_deviations>

This project has now hit that limitation twice. 49-CONTEXT.md D-09 marks this decision one-way and 49-RESEARCH.md Pitfall 5 flags it as the phase's single irreversible door. Confirm the vocabulary before the door is walked through; after 0028 merges there is no cheap fix.
  </context>
  <options>
    <option id="four-values-as-specified">
      <name>Ship the four values exactly as locked in D-09: unreviewed, needs_review, operator_confirmed, operator_edited</name>
