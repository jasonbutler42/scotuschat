<planner_decisions>
**Which UAT sub-item wins at narrow widths: NEITHER has to lose.** 49-UAT.md flags sub-item 5 ("all five StatCards sit evenly in one row" — operator PASSED it) and sub-item 7 ("no horizontal scroll at 375px" — FAIL) as being in direct conflict, and asked the plan to state which wins. The honest answer is that they conflict only under a **fixed** five-column grid. Run the arithmetic on the dashboard's real geometry:

- The dashboard content region is `max-width: 860px` with `padding: 48px 24px`, so its inner width is `min(viewport, 860) − 48`.
- At any viewport ≥ 908px the inner width is **812px**. Today's `repeat(5, 1fr)` with `gap: 32px` therefore already gives each card `(812 − 4×32) / 5 = 136.8px`. The cards were never 180px+ wide; they have always been ~137px.
- `repeat(auto-fit, minmax(120px, 1fr))` with the same `gap: 32px` fits `⌊(812 + 32) / (120 + 32)⌋ = ⌊844/152⌋ = 5` tracks at 812px, and with exactly five items every track is filled and stretches to `1fr` — **136.8px each, byte-identical rendering to today**. Sub-item 5 is preserved exactly, not conceded.
- At a 375px viewport the inner width is `327px`, which fits `⌊(327 + 32) / 152⌋ = 2` tracks at `147.5px` each — *wider* than the desktop card. No overflow. Sub-item 7 is satisfied.

So `120px` is the load-bearing number, and the reason it works is that the desktop cards are already narrower than a naive floor would assume. A floor of `180px` would collapse the desktop grid to three columns and silently break sub-item 5. That is exactly the failure mode a comment cannot prevent, so Task 2 encodes the arithmetic as a test that parses the floor and the gap out of the source and asserts the track count at both widths.

**Everything else uses ONE mechanism: container scroll, never body scroll.** CLAUDE.md's conventions and this project's admin idiom favour letting genuinely-wide content scroll inside its own container over letting the page body scroll, and 49-UI-SPEC E1/E2/E6 forbid truncation outright (truncating a discrepancy value could hide the exact disagreement the operator is being asked to adjudicate). So the two tables and the status segment group each get their own `overflow-x: auto` block. Nothing is clipped, nothing is ellipsised, no `nowrap` is removed, and the reading experience at desktop width is unchanged.

**Rejected alternatives, recorded so they are not re-proposed:**
- *A `@media` query, or a Svelte `<style>` block with element selectors.* D-29 locks the inline-style idiom for this phase, and `test_no_class_attribute_anywhere_inline_styles_only` guards it on the review page. A scoped `<style>` block also injects a compiler-generated class into the built output, which is the same thing that guard exists to prevent.
- *`gap: clamp(12px, 3vw, 32px)` on the dashboard grid.* Tempting because it is inline and media-query-free, but `3vw` is keyed on the **viewport**, not the container, so at a 900px viewport the gap would silently become 27px and the "even 32px gaps" claim in 49-UI-SPEC E8 and UAT sub-item 5 would become conditional on window size. Rejected: the `auto-fit` floor solves it without touching the gap at all.
- *`flex-wrap: wrap` on the status segment group.* Would work geometrically but breaks the segmented control's appearance: the first button carries `border-radius: 6px 0 0 6px`, the last `0 6px 6px 0`, and the middle four `border-left: none` — a wrapped second line would show a detached, half-rounded fragment with a missing left border. Container scroll preserves the control's shape.
- *Removing `white-space: nowrap` from the table cells so they wrap instead.* Explicitly forbidden by 49-UI-SPEC E1/E2 (`nowrap` is applied only to the short docket/date/badge cells, and that treatment matches every existing admin table) and it would not even fix it — six columns of wrapped text still exceed 327px.
