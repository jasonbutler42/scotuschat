<planner_decisions>
**G-49-3 CANNOT be planned deterministically without a locked decision, and here is exactly why — the reason is narrower and better-evidenced than "the semantics are undefined."**

The semantics of BENCH↔ADVOCATE reassignment are **already locked and already shipped** — on a different surface:

- `api/services/admin_jobs.py::update_resolve_row_for_job` (`:852`) states in its own docstring: *"Update ArgumentParticipant.side (BENCH allowed) … unlike admin_arguments.update_participant_side, which rejects BENCH by design."* It drops `descriptor` from the UPDATE when `body.side == SideEnum.BENCH` (`:926-929`) — RESOLVE-13's "hidden, not shown, not cleared."
- `app/src/lib/components/ResolveCard.svelte` already ships the full control: `toggleSide` / `confirmSide` (`:269-313`), a side gate, `sideBucket` / `lastSideBucket` (`:245-268`) which clears a carried-over `personId` when the row crosses the BENCH/ADVOCATE boundary because the two candidate pools are disjoint (RESOLVE-09), and `lastAdvocateRole` to restore the prior advocate role on the way back.
- `create_person_for_job` sets `Person.is_justice` from `body.side == BENCH` (`api/services/admin_jobs.py:1120`).

So the operator can already reclassify bench↔advocate — on `/admin/pipeline/{job_id}`. What they cannot do is it from the Speakers card, and the reason is a **named security disposition**:

- `api/services/admin_arguments.py:755` — `raise ValueError("BENCH cannot be set via participant side update")`, documented at `:735` as *"BENCH guard (T-15-02-BENCH)"*, and mirrored in `api/schemas/admin_arguments.py:49` and `api/routers/admin.py:1444`.
- `T-15-02-BENCH` was minted in Phase 15's threat register (`15-02-PLAN.md:207`, Tampering, severity medium, disposition mitigate: *"Service raises ValueError when side == BENCH → 422; BENCH is not operator-settable on advocates"*).
- Phase 25 then **explicitly declined to relax it**: `25-01-SUMMARY.md:177` — *"`update_resolve_row_for_job` is intentionally a new function/endpoint rather than an extension of `admin_arguments.update_participant_side`, because that existing endpoint explicitly rejects BENCH by design (T-15-02-BENCH) — reusing it would require weakening an existing security guard."*
- `api/tests/test_admin_arguments_service.py:1535-1539` asserts the rejection.

**Therefore the real question is not "what should reassignment mean" — it is "do we relax T-15-02-BENCH on the argument-edit surface, or route the operator to the surface where the control already legitimately exists?"** That is a security-disposition decision the project has already answered twice in the other direction, so a planner must not flip it unilaterally. Hence the checkpoint.

Three further facts that shape the options, all found in source:

1. **The bench branch is a one-way trap today.** `_bench_role_and_missing_tenure` is only called when `participant.person_id is not None`; for a NULL person it short-circuits to `(None, False)` (`api/services/admin_arguments.py:288-296`), so a BENCH row with no person renders a bare `—` with no "Missing tenure" warning and no Edit-person link. Any option that lets a row move INTO bench must also give a bench row a way back out, or the operator can strand a participant.
2. **There is a second, non-reconciled `is_bench` source of truth.** The admin path derives it from `side == SideEnum.BENCH`; the public chat page derives its own from `tenure.length > 0` (`app/src/routes/cases/[slug]/arguments/[id]/+page.server.ts:36`). A BENCH participant with no `CourtTenure` would read bench in admin and advocate in public. This is the open pending todo `2026-08-12-speakers-bench-classification-silent-fallback.md`; reconciling it touches the public read path, which is outside Phase 49's boundary, so both options leave it as-is and say so.
3. **49-06 D6 does not gate this surface.** `resolveCardReadonly` / `metadataReadonly` live only on `app/src/routes/admin/pipeline/[job_id]/+page.server.ts:312-313`. The argument edit page's Speakers card has no readonly gating at all — its Save is gated solely on the row's side still being unresolved. The operator's UAT-test-10 ratification (every unpublished state editable, only PUBLISHED read-only) must not be re-narrowed, and neither option introduces a new editability axis.
4. **D-20's provenance hole does not apply.** `deferred-items.md` records that no locked decision exists for what `source`/`method` an admin-driven resolve should stamp — but D-22 settles it for this path: an operator edit does NOT overwrite stored `source`/`method`; operator authority is carried entirely by `review_state`. `update_participant_side` already implements exactly that (`api/services/admin_arguments.py:794-808`). So a side write from this surface needs no new provenance decision.

**Recommendation: `deep-link`.** Not because `port-control` is hard — it is small and its semantics are pre-locked — but because `deep-link` is the only option that does not spend a security disposition the project has twice paid to keep, does not create a second implementation of side/candidate-pool logic (the open todo `2026-08-12-speaker-popover-frontend-duplication-cleanup.md` warns against precisely that duplication), and is this phase's own shipped principle: D-23, *"Confirm is inline; edit deep-links… Rebuilding the hardest UI in the app in a second place was rejected."* The operator may reasonably weigh their one extra click higher; that is their call, not the planner's.

**WR-01's behavioural question is small enough to answer here, and it is answered: resync on OPEN, not on every prop change.** 49-REVIEW.md's own suggested fix (`:327-334`) is the same. Resetting on open cannot lose operator input, because the popover is closed and no input exists. Resetting on *every* `initialSide` change would discard a radio choice the operator deliberately made while the popover was open — a worse bug than the one being fixed. So no `$effect` tracking the prop; one branch on the open transition.

**No tracer task.** TRACER_MODE is on; 49-01's tracer already threaded this phase's architecture and every layer either option touches is shipped. There is no new layer to thread.
