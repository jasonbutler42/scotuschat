# Phase 49 — UI Design Contract

> Visual and interaction contract for the new `/admin/review` operator review queue.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This phase has no shadcn/component-library decision to make** — see Design System
> table below. Per `49-CONTEXT.md` D-29, this screen is built in today's hand-rolled
> admin idiom (inline styles, `.planning/codebase/DESIGN-SYSTEM.md` palette), extending
> the exact patterns already shipped on `/admin/arguments` and `/admin/people` — no new
> abstractions, no component library. This spec's job is to name the *specific* extension
> points (four new `review_state` badge colors, one discrepancy indicator, the queue's
> layout, filters, and copy) that CONTEXT.md left as implementation detail or discretion.

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — hand-rolled Svelte 5 (Runes) components with inline `style` attributes, established codebase-wide since Phase 5. Tailwind is present in `app/package.json`/`app/tailwind.config.js` and imported in `app/src/app.css` (`@tailwind base/components/utilities`) but is **not used** by any admin page — confirmed via `grep -rohE "#[0-9a-fA-F]{6}"` across `app/src/routes/admin/**` and `app/src/lib/components/**`, which returns only inline hex literals, never a Tailwind utility class. Do not introduce Tailwind classes on this screen; match the surrounding files. |
| Icon library | none — inline hand-drawn SVG per icon, matching `CopyableExtractedValue.svelte:111-114`'s copy icon (`viewBox="0 0 24 24" stroke="currentColor" stroke-width="2" fill="none"`) and the Unicode glyphs already in use (`⚠` warning, `◌` spin, `✓` success). This phase needs no new icon — the expand/collapse disclosure reuses **text**, not a chevron (see Interaction Contract). |
| Font | inherited app-wide (`system-ui, -apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif`, declared once in `app/src/app.css`) — no phase-specific font decision. |

**shadcn gate rationale:** SvelteKit/Svelte 5, not React/Next.js/Vite+React — shadcn (a React-only tool) does not apply. No `components.json` exists anywhere in `app/`. 44+ prior phases, including the two closest analogues to this one (`/admin/arguments` segmented-filter list and `/admin/people` tabbed list), establish the hand-rolled inline-style Svelte pattern as the project's actual, load-bearing design system. `49-CONTEXT.md` D-29 explicitly declines a `/gsd-ui-phase` layout pass or shared-component extraction here — Phase 51 owns that. This UI-SPEC therefore extends the existing system rather than picking a tool.

## Spacing Scale

Declared values (must be multiples of 4) — all reused verbatim from the existing codebase, no new spacing values introduced:

| Token | Value | Usage on this screen |
|-------|-------|-----------------------|
| xs | 4px | Gap between the trust-tier badge and status badge on a queue row; gap between a badge's border and its text |
| sm | 8px | Gap between the case-name and docket cells; gap between the Confirm/Edit/Re-flag action buttons on a constituent row; table cell horizontal padding |
| md | 16px | Field-to-filter gap in the header's filter row; margin between the tab bar and the filter row; gap between an expanded row's stacked constituent blocks |
| lg | 24px | Card/page-section internal padding (empty-state card, filter-row container) — matches every existing admin card |
| 2xl | 48px | Page content top/bottom padding (`<div style="max-width: 860px; margin: 0 auto; padding: 48px 24px;">` — the exact container every other admin list page uses; this screen reuses it unchanged) |

Not used on this screen (declared for completeness, per the template's full 8-point scale; no exception, simply no use case here): **32px** (used elsewhere for the dashboard's stat-card grid gap, not needed by a single-column table+filter layout) and **64px** (no use case anywhere in the admin UI today).

Exceptions (both pre-existing conventions, carried forward unchanged, not re-litigated):
- Primary/segmented-control buttons and the Confirm/Edit row actions on a **table** row use **36px** `min-height` (the documented "compact per-row inline buttons inside dense tables" exception) — matches the Remove/Change/Edit-link precedent throughout `ResolveCard.svelte` and `admin/arguments/+page.svelte`.
- Tab buttons (Arguments | People) and the segmented status control use **44px** `min-height`, matching the People page's Bench/Advocate tabs and the Arguments page's status segmented control exactly.

## Typography

No new sizes or weights — this phase reuses the app-wide 3-size, 2-weight scale exactly as documented in `.planning/codebase/DESIGN-SYSTEM.md`:

| Role | Size | Weight | Line Height | Usage on this screen |
|------|------|--------|-------------|------------------------|
| Heading | 20px | 600 | 1.2 | Page `<h1>` "Review", `<h2>` inside the empty-state card |
| Body | 16px | 400 | 1.5 | Case name / person full-name cell text, constituent name text inside an expanded row |
| Label / meta | 14px | 400 | 1.4 (badges/pills) or 1.5 (paragraph meta) | Table column headers, docket/date cells, badge text, filter `<select>` labels, discrepancy incoming/existing value lines, "Show details"/"Hide details" toggle |

Badge text specifically uses **12px** — this is not a new size on the *typography* scale (it is the existing tier-badge convention already shipped on `admin/arguments/+page.svelte`'s `tierBadgeStyle`, a smaller "secondary/informational" treatment distinct from the 14px primary status badge). No new type size is introduced by this phase; the review-state badge simply follows the tier badge's existing 12px convention rather than the 14px status-badge convention, since it is informational in the same way tier is.

**New colors this phase — four `review_state` badge colors plus one discrepancy indicator, chosen to be visually distinct from every hex already in use** (confirmed against the full existing inventory: `#0f1117 #1e293b #334155 #34d399 #38bdf8 #4ade80 #64748b #93c5fd #94a3b8 #a78bfa #cbd5e1 #d97706 #e2e8f0 #ef4444 #f59e0b #f87171 #facc15 #fb923c #fbbf24 #fcd34d`):

| `review_state` value | Color | Label | Rationale |
|---|---|---|---|
| `unreviewed` | **`#475569`** (new — slate-600) | "Unreviewed" | The majority/default state on a large corpus (D-04's volume tension) — deliberately the calmest, least-attention-grabbing tone on the row, distinct from the existing `#64748b` tier-fallback grey and `#94a3b8` muted-text/candidate grey so it never gets misread as either |
| `needs_review` | **`#fbbf24`** (reused — existing Warning role) | "Needs review" | Exact semantic match: DESIGN-SYSTEM.md already documents `#fbbf24` as "Missing tenure text, other attention-needed inline warnings" — this *is* that role, not a new one, so it is reused rather than assigned a new hex |
| `operator_confirmed` | **`#2dd4bf`** (new — teal-400) | "Confirmed" | Deliberately not the trust-tier greens (`#34d399` trusted, `#4ade80` published) or blue (`#38bdf8` verified) it sits beside on the same row — a human-confirmed value is a *different claim* than a high trust tier and must not be visually conflated with one |
| `operator_edited` | **`#e879f9`** (new — fuchsia-400) | "Edited" | Distinct from `operator_confirmed`'s teal (an edit is a different action than a confirm, per D-11) and from draft's violet (`#a78bfa`) and destructive red — reads as "changed," not "wrong" or "in-progress" |
| discrepancy present (any open row) | **`#fb7185`** (new — rose-400) | "Discrepancy" | A third, distinct warm-attention tone — deliberately not `#fbbf24` (needs_review) or `#ef4444`/`#f87171` (destructive/uncertain), because a row can be `needs_review` **and** carry an open discrepancy at once (D-05's two independent inclusion legs), and the two badges must read as different facts, not duplicates |

Badge rendering formula (all five, plus the existing tier badge they sit beside) is the **existing `tierBadgeStyle` formula verbatim** — do not invent a new badge shape:
```
border: 1px solid {color}; border-radius: 4px; padding: 2px 8px; font-size: 12px; font-weight: 400; background-color: #0f1117; color: {color}; display: inline-block;
```

Accent (`#93c5fd`) reserved for: the page heading, the active Arguments/People tab fill, the active "All" segment of the status control, the "Confirm" action button, the "Edit" deep-link, and the "Show details"/"Hide details" toggle. Never used on any badge (status, tier, review-state, or discrepancy) — matches the existing rule verbatim.

Destructive (`#ef4444`) reserved for: nothing new. This screen introduces no destructive action of its own (see Copywriting Contract).

## Screen Contract — `/admin/review`

### Layout (top to bottom, matches the existing admin-page skeleton exactly)

1. **Header bar** (`background-color: #1e293b; border-bottom: 1px solid #334155; padding: 16px 24px;`): `<h1>Review</h1>` (20px/600) + the Arguments\|People tab pair, same row, same flex-wrap treatment as `admin/people/+page.svelte`'s header.
2. **Filter row**, inside the `max-width: 860px` centered content container, `margin-bottom: 16px`, `display: flex; flex-wrap: wrap; gap: 16px; align-items: center;`:
   - Status segmented control (5 segments: All/Candidate/Draft/Published/Unpublished) — **Arguments tab only**. Reuses `filterButtonStyle` verbatim from `admin/arguments/+page.svelte`, extended with a 5th segment.
   - Trust-tier `<select>` — **Arguments tab only** (People rows have no `trust_tier`; see UI Considerations "partial" row for why this filter is hidden, not disabled, on the People tab).
   - Review-state `<select>` — **both tabs**. Style: the plain `<select>` formula already used at `admin/people/[id]/+page.svelte:908-922` (`background-color: #1e293b; border: 1px solid #334155; border-radius: 6px; padding: 8px 12px; font-size: 16px; color: #e2e8f0; box-sizing: border-box;`), each `<option>` labeled per the Copywriting Contract above.
   - All three filters apply immediately on change via `goto()` (an `onchange` handler, no separate "Apply" button) — the exact idiom every existing filter on this codebase uses (status segments, Bench/Advocate tabs, missing-field pills, tenure-gaps toggle). Filters compose as URL query params (`?status=&tier=&review_state=`) so they are back-button-safe and linkable, matching `admin/arguments`'s `?status=` precedent.
3. **Active-filter indicator** ("Showing: {filters} · Clear filter") — reuses the exact pattern and copy shape from `admin/arguments/+page.svelte:206-226`, extended to name whichever of the up-to-three active filters are set (e.g. "Showing: Uncertain tier, Needs review · Clear filter").
4. **Empty state** — reuses the exact bordered-card empty-state shape from `admin/arguments/+page.svelte:230-248` (`background-color: #1e293b; border: 1px solid #334155; border-radius: 8px; padding: 24px; text-align: center;`), with the copy from the Copywriting Contract above.
5. **Table** (populated state) — `<table style="width: 100%; border-collapse: collapse;">`, `scope="col"` on every header (WCAG 1.3.1, matching every existing admin table).

### Arguments tab — table shape

Top-level row columns, exact order: **Tier badge + Status badge | Case name | Docket | Argued date | Needs-attention | Expand.**

- Sort order (D-03): worst tier first (UNCERTAIN → PROVISIONAL → TRUSTED; VERIFIED and above never appear unless a discrepancy-only leg puts them here), then oldest `argued_date` within tier — implemented server-side, not client-side, matching every other admin list's sort-in-the-query convention.
- The Tier badge and Status badge sit together in the first cell exactly as they already do on `admin/arguments/+page.svelte:332-337` (`<span style={tierBadgeStyle(...)}>` then `<span style={badgeStyle(...)}>`, 4px gap) — reused verbatim, including the Candidate badge convention.
- "Expand" is the "Show details"/"Hide details" text toggle from the Copywriting Contract, `aria-expanded` on the toggle button, controlling a full-width `<tr>` rendered immediately below — the exact "full-width row beneath the triggering row" technique already used for the publish-blocked panel on `admin/arguments/+page.svelte:492-618`. Do not use a native `<details>` element (it cannot legally wrap a `<tr>`).
- **Expanded row content** — one block per flagged constituent (D-01), each block:
  - Constituent identity: person full name (or "Unresolved speaker" if `person_id IS NULL`) + the side/role hint (Bench/Advocate — reuses `SpeakerPopover`-adjacent wording, not a new vocabulary).
  - `review_state` badge (the four new colors above).
  - Discrepancy badge, when the constituent carries at least one open (`resolved_at IS NULL`) discrepancy — see "Discrepancy detail" below.
  - Actions, in this fixed order, `display: flex; gap: 8px;`: **Confirm** (accent, 36px), **Confirm as unattributable** (muted/secondary, 36px — renders only when `person_id IS NULL`, per D-17), **Edit** (accent text link, deep-links to `/admin/arguments/{id}` and scrolls/anchors to the Resolve card row for that constituent, per D-23), **Re-flag for review** (muted text link, renders only when `review_state ∈ {operator_confirmed, operator_edited}`, per D-25).

### People tab — table shape

Top-level row columns, exact order: **review_state badge | Full name | Provenance note | Actions.**

- No tier badge, no status badge (Person carries neither) and no trust-tier filter (see filter row above) — this is a direct, reasoned extension of D-02's own logic ("a person spans many arguments... the two entity shapes need different columns"), applied here to *filters* as well as columns, since `trust_tier`/`status` are argument-level concepts that have no meaning on a bare `Person` row (48 D-10's no-fan-out rule). **LOCKED — confirmed by the operator during the step 9.5 probe pass (2026-08-21); no longer an open inference.**
- No expand/collapse — a `Person` row has nothing to fan out to (no constituents-of-a-constituent); the row is already a single item, matching D-02's flat-columns reasoning.
- Sort order: `needs_review` first, then `unreviewed`, then alphabetical by full name — extends D-03's "worst state first" principle to a screen with no tier axis. **LOCKED — confirmed by the operator during the step 9.5 probe pass (2026-08-21).**
- "Provenance note" cell: a short, non-interactive line reading the row's `source`/`method` (e.g. "Corpus · direct") in 14px muted text — **not** wrapped in `CopyableExtractedValue` (that component's copy-to-clipboard affordance has no purpose here; there is nothing to paste this value into) — plain `<span>` only.
- Actions: **Confirm**, **Edit** (deep-links to `/admin/people/{id}`), **Re-flag for review** (when already reviewed) — no "Confirm as unattributable" on this tab (D-17 is specifically about the unresolved-speaker floor, an `ArgumentParticipant` concept; a bare `Person` row has no analogous "unattributable" state).

### Discrepancy detail (within either tab's expanded/row content)

When a constituent or person row carries one or more open discrepancies, render the "Discrepancy" badge (`#fb7185`) plus, directly beneath it, one line per open discrepancy:

```
{field}: existing "{existing_value}" ({existing_source}/{existing_method}) — incoming "{incoming_value}" ({incoming_source}/{incoming_method})
```

14px, primary text (`#e2e8f0`) for the values, muted text (`#94a3b8`) for the field name and the parenthetical source/method — plain text, no `CopyableExtractedValue` (there is no single "the" extracted value here; there are two competing values, which is the discrepancy itself, so the copy-button affordance would be misleading about which one is "the" value). Per D-15, resolving the row (Confirm, Confirm as unattributable, or a saved Edit) closes every open discrepancy on that row in the same transaction — no separate accept/reject control per discrepancy line.

### Dashboard + nav entry points (D-27, D-30)

- `AdminSubNav.svelte` gains a "Review" link between "Arguments" and "People Editor", identical styling to its siblings.
- The admin dashboard (`admin/+page.svelte`) gains a fifth `StatCard` (title "Review queue"), using the exact `StatCard` snippet-body pattern already shown for "Arguments"/"People"/"Utterances"/"Pipeline runs" — a large count (`formatCount`, N/A-on-failure) plus one link ("{N} items need review →", accent, 44px) to `/admin/review`. Backed by a dedicated `COUNT` query (this spec's discretion-lean, matching `49-CONTEXT.md`'s own lean) — never derived from fetching the unbounded queue list just to produce a number.

### ⚠ Unresolved — planner must treat as assumption

These are genuine gaps the probe surfaced that this spec does not answer. Each is a real
state the implementation will hit. The planner must either resolve it in a task or record
it as an explicit assumption — it must not be treated as specified.

- **⚠ unresolved — planner must treat as assumption** · `empty` (Empty / no data) on **Expanded constituent blocks** (E5)
  An argument queued SOLELY because its `trust_tier` is below TRUSTED (D-06's published-but-degraded leg) has zero flagged constituents, so the expanded panel has no constituent blocks to render. The spec does not say what that expanded panel shows — nor whether the "Show details" toggle should render on such a row at all.
- **⚠ unresolved — planner must treat as assumption** · `overflow` (Overflow / truncation) on **Row action buttons** (E7)
  All four actions (Confirm / Confirm as unattributable / Edit / Re-flag for review) can co-render in a single dense table cell — an unresolved-speaker constituent that has already been confirmed hits exactly that case. `display: flex; gap: 8px` with 36px buttons is specified, but no wrap or narrow-viewport behavior is, so the action row can overflow the 860px container.
- **⚠ unresolved — planner must treat as assumption** · `empty` (Empty / no data) on **Dashboard "Review queue" StatCard** (E8)
  At N=0 the StatCard link renders "0 items need review →", inviting the operator into an empty queue. The spec defines no zero-state variant — whether to suppress the link, or render a non-link "No items need review" — so the dashboard advertises work that does not exist.
- **⚠ unresolved — planner must treat as assumption** · `zero-one-many` (Zero / one / many) on **Dashboard "Review queue" StatCard** (E8)
  The link template "{N} items need review →" renders "1 items need review" at N=1. Singular/plural handling is locked for the per-row attention count but NOT for this StatCard link.

### 🧪 Backstop — resolved, but verified only by an explicit test

Each carries `verification: backstop`: a statement the spec asserts but no shipped fixture
exercises. At verify time, one with no wired evidence routes to
`insufficient_spec → human_needed` rather than silently passing.

- `zero-one-many` on **Arguments tab queue table** (E1) — { statement: "The Copywriting Contract locks the plural wording '{N} constituent{s} need review', but no corpus fixture with exactly 1 versus many flagged constituents on a single argument exists yet. Backstop: a held-out test asserting both the singular and the plural string render correctly.", verification: backstop }
- `zero-one-many` on **Expanded constituent blocks** (E5) — { statement: "A single argument may expand to one constituent block or to many; block spacing is specified as 16px (`md`) but no fixture exercises the one-block versus many-block layout. Backstop: the same held-out test as E1's count assertion, extended to the expanded-panel layout.", verification: backstop }
- `partial` on **Discrepancy detail lines** (E6) — { statement: "A discrepancy where either side is absent — a newly-populated field has no existing value, or a cleared field has no incoming value — would render as `existing '' — incoming '…'`. The line template assumes both sides are present. Backstop: a test asserting the one-sided-discrepancy rendering is legible and does not print an empty pair of quotes.", verification: backstop }
- `long-text` on **Discrepancy detail lines** (E6) — { statement: "A `last_name` / `name_suffix` / `full_name` discrepancy can carry an unusually long incoming value (e.g. a malformed corpus string). The wrap-never-truncate rule above is prescribed but untested.
