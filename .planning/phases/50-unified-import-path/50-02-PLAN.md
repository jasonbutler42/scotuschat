<decision_record>
**OQ-1 (operator, 2026-08-25) — LOCKED.** `Argument` and `Case` carry nullable `source`/`method` (shipped by plan 50-01). A new `apply_argument_value_change` is a true peer of the two existing gate functions, and disagreements get a real discrepancy-recording home via Phase 49's review model. No backfill. NULL means unknown and the gate must fail closed on it. This plan states the chosen NULL semantics explicitly and tests them.

**PD-06 — `apply_case_value_change` ships alongside `apply_argument_value_change`.** D-02's compare set includes lead `Case.case_name` and `Case.docket_number`, and plan 50-01 put `source`/`method` on `cases` for exactly that reason. One function per table mirrors the existing shape (`apply_participant_value_change`, `apply_person_value_change`) rather than inventing a generic table-agnostic gate, which would need a table registry and would be a second, subtly-different gate in all but name.

**PD-07 — the chosen NULL semantics, stated for the record.** For `Argument`/`Case` the gate reads existing authority as follows. If the stored value is populated and the row's `source` is NULL, the stored provenance is genuinely unknown — the row was written by a writer that predates this phase or did not declare — and the gate FAILS CLOSED: it never writes, and it records the disagreement. It does not hand `("", "")` to `decide_write`, because `authority_rank("", "", "")` is `UNKNOWN` (rank 0) and CORPUS (rank 3) strictly outranks it, which would let a corpus re-import clobber an unstamped operator edit. That is precisely the outcome OQ-1 forbids. This fail-closed rule is implemented in the two new gate functions only; it does NOT change `decide_write`, and it does NOT change `apply_participant_value_change` / `apply_person_value_change`, whose Phase 49 behavior is frozen and exhaustively tested.

**PD-08 — `Argument`/`Case` have no `review_state`, so operator authority is read off `source == "operator"`.** Phase 49's D-22 rule ("an operator edit does not rewrite a row's stored provenance; operator authority is carried by `review_state`") is scoped to the two tables that HAVE a `review_state`. `Argument` and `Case` do not, and OQ-1 deliberately did not add one. The only expressible authority home on those two tables is the `source` column, so `update_argument` and `update_argument_metadata` must stamp `source=operator` / `method=manual` on the fields they write — plan 50-03 owns that stamping. This gate passes `existing_review_state=""` for both tables and relies entirely on `authority_rank`'s rule 2. Recorded as a deliberate, scoped deviation from D-22, not an oversight.

**PD-13 — the gap-fill rule applies to ALL FOUR gates, not only the two new ones.** `decide_write`'s own docstring states its ACCEPT outcome covers the case where "the stored side is empty/blank", but `decide_write` never receives the values — only `values_differ` — so it structurally cannot implement that clause; it is an instruction to callers that no caller implements today. The consequence is concrete: a blank stored value plus a non-blank incoming value yields `values_differ=True` and CORPUS(3) outranking UNKNOWN(0) or an unreviewed Person, so filling a gap returns ACCEPT_AND_RECORD and mints a `value_discrepancy` row for a non-event. Plans 50-05 and 50-06 route two existing blank-only prefills through the gate (`import_convokit._apply_extracted_name_provenance` and `import_justices_csv`'s Person prefill), and `parse.py`'s two blank-only conditional writes; without this rule each reseed would mint thousands of discrepancy rows whose only resolution is "still fine" — the exact flood D-03's reasoning and Phase 49's D-24 rejection of bulk confirm both exist to avoid. So the rule is implemented once, as a shared helper, and applied in all four gate functions.

**PD-09 — a fifth leg on `_argument_attention_predicate`.** D-07's rationale for leaving `review_state` untouched on an accepted overwrite is that "the recorded discrepancy already pulls the argument into `/admin/review` through the attention predicate 49-06 added". Verified at plan time: that predicate's discrepancy leg filters `target_type == "argument_participant"` only, so an argument-level or case-level discrepancy satisfies none of its four legs and would be recorded but invisible. This is the same class of defect 49-06 found live during D-32's walkthrough. The fifth leg closes it before the writer that produces those rows ships in plan 50-04.
</decision_record>
