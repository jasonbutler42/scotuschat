<decision_record>
**PD-10 (restated — this plan implements it).** The approve surface is `/admin/review`, not `/admin/arguments`. Verified at plan time: `list_arguments` filters to DRAFT/PUBLISHED/UNPUBLISHED, so a freshly-imported CANDIDATE corpus argument does not appear in `/admin/arguments` at all, while `/admin/review`'s status filter set includes `candidate` and the screen was built in Phase 49 for exactly this sweep.

**D-20 (operator, locked in 50-CONTEXT.md) — no argument-scoped resolve or create-person parity.** The evidence that settled it: the corpus path's only unresolved participants are ConvoKit's unattributable sentinels (`type == "U"`), which the importer never mints a Person for by design, and `/admin/review` already ships confirm-as-unattributable for exactly those. Every identifiable corpus speaker gets a Person at import. So the argument-scoped approve is the only new action this screen needs, and no Resolve or Create-person affordance is added here. Revisit only if a corpus participant ever needs person REASSIGNMENT with no job to do it from.

**PD-12 — the approve action goes in the expanded panel's action row, not the collapsed row.** The collapsed row is a scannable list; the existing confirm / confirm-as-unattributable / re-flag actions all live in the expanded panel's action row. Putting approve there keeps one action location and avoids an accidental click on a lifecycle transition while scanning.
</decision_record>

| T-50-16 | Information Disclosure | `FASTAPI_BASE_URL` or `ADMIN_TOKEN` leaking to the client bundle | high | mitigate | Both come from `$env/static/private` inside `+page.server.ts`; no `PUBLIC_` prefixed variable is introduced (CLAUDE.md Architecture Rule 2), asserted by a zero-count grep |
