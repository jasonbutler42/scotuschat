<objective>
Make the two identity facts the operator now depends on legible on the admin person page —
which name form drives utterance attribution, and whether this person is corpus-joined — without
making either of them writable.

Purpose: `oyez_speaker_id` is now the load-bearing join key and the thing that makes a duplicate
structurally impossible, and `display_name` silently changes what a Justice's bubbles say. Both
were invisible in the admin UI. D-09/D-10 make them visible and read-only; D-11 deliberately
leaves the People directory listing alone.

Output: two fields on `PersonDetail`, two on the hand-maintained TypeScript interface, two
`<output>` rows in the Identity card, and a schema test proving neither reached `PersonUpdate`.

**How the visual is verified.** `CLAUDE.md`'s Testing Policy is explicit that frontend behavior is
verified by the operator's eye or a real browser, or it is not verified — and unlike the public
argument page, the admin person page sits behind session auth with no existing browser harness, so
building one for two read-only rows would cost more than it proves. The operator's eye is the right
instrument. This project runs `workflow.human_verify_mode` at its default `end-of-phase`, so the
eye-check is carried as a `<verify><human-check>` on Task 2 rather than as a mid-flight
`checkpoint:human-verify` task — the verifier harvests it into the phase UAT batch, and the plan
stays autonomous. Everything the schema layer can prove mechanically is proven mechanically in
Task 1, so the human check is about placement and treatment only, never about correctness.
</objective>

carries `ConfigDict(extra="forbid")`; leaving both fields out is what produces the 422 and is the
entire mechanism by which a re-seed can never collide with an operator edit. Do not add them to
`PersonCreateRequest` either.

Mirror both fields onto the hand-maintained TypeScript `PersonDetail` interface in
`app/src/routes/admin/people/[id]/+page.server.ts` as `display_name: string | null;` and
`oyez_speaker_id: string | null;`. There is no shared-type codegen between FastAPI and SvelteKit
in this repo, so the Pydantic edit and the TypeScript edit are two line items in one task — a
schema-only change leaves the Svelte page reading `undefined` at the type level while the JSON
payload carries the value.

Create `api/tests/test_admin_people_schema_readonly.py` — named after the unit under test, no
phase number — covering the four `<behavior>` bullets. Assert the 422s through the real request
path, not by inspecting `model_fields` alone, so the test proves the refusal rather than the
declaration.
