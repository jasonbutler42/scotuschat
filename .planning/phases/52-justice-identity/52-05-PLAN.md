<objective>
Stop the reset from asserting things it does not know, and stop it from looking like a hang.

Purpose: two folded todos and two locked decisions. `RESET_MID_ERROR` today claims probable
database corruption for every failure mode — including the backend's own 503 corpus-missing case,
where the pre-flight ran and nothing was deleted, and including the observed case where the reset
fully succeeded and only the client stopped listening. D-14 replaces "which code path failed" with
"what a follow-up read actually found". D-15 gives the operator a progress signal for an operation
measured at 3m13s of database writes, now longer with the justice seed added.

Output: one dev-only GET that answers both questions, a SvelteKit proxy for it, four evidence-based
outcomes replacing two guesses, a per-fixture progress line, and an amendment note on the Phase 43
UI-SPEC whose lock this lifts.

**Constraint reconciliation — "Pipeline is offline only".** `CLAUDE.md` forbids exposing pipeline
steps as HTTP endpoints or user-facing features. The new surface is a **read-only GET** that runs
no ingest, parse or resolve step: it re-runs the same per-conversation existence-and-state SELECT
`reset_to_fixture` already performs internally, and reads an in-memory progress record. It
triggers nothing. The destructive POST it accompanies already exists and was already accepted as a
deliberate dev-only exception in Phase 43, gated by `api/main.py`'s development-only
`include_router`. The new GET inherits that same gate, so it is genuinely absent in every other
environment. This is compliant with both the offline-pipeline constraint and the "FastAPI is
read-only" architecture rule, and the reconciliation is recorded here so a later reader does not
have to reconstruct it.

**Canon-referral breadcrumb (prohibition probe).** "A dev-only endpoint must not be reachable in
production" is canon security, already owned by the `api/main.py` environment gate and pinned by
`tests/test_admin_dev_router_gate.py`; not minted as a bespoke prohibition here, only re-verified.

**How the visual is verified.** The reset is a destructive operator tool whose whole point in this
plan is what the operator reads while it runs and after it fails, and the Testing Policy puts
frontend behavior in front of the operator's eye or a real browser. There is no browser harness
behind admin session auth, so the operator is the instrument. This project runs
`workflow.human_verify_mode` at its default `end-of-phase`, so the operator run is carried as a
`<verify><human-check>` on Task 2 rather than as a mid-flight `checkpoint:human-verify` task — the
verifier harvests it into the phase UAT batch, and the plan stays autonomous. Everything the
backend can prove mechanically is proven in Task 1.
</objective>
